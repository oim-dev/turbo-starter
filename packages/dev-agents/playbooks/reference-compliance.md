# Проверка соблюдения React и Next.js Reference

Цель — установить, что исполнитель действительно применил обязательные подходы скиллов,
а не только написал работающий код. Этот протокол дополняет [общий протокол](review.md)
и обязателен для `react-reviewer` и `nextjs-reviewer`.

## Определи действующие нормы до чтения решения

- Для React SPA прочитай [инструкции приложения](../../../apps/react-admin-panel/AGENTS.md),
  загрузи [react-reference](../../../.agents/skills/react-reference/SKILL.md) и
  [unit-architecture](../../../.agents/skills/unit-architecture/SKILL.md), затем прочитай
  архитектурный профиль и документы затронутых прикладных областей.
- Для Next.js прочитай [инструкции приложения](../../../apps/next-web-app/AGENTS.md),
  загрузи [nextjs-reference](../../../.agents/skills/nextjs-reference/SKILL.md) и
  `unit-architecture`, затем прочитай профиль App Router и локальные уточнения.
  `react-reference` не является нормативным источником для Next.js.
- Для TypeScript/TSX загрузи [ts-styleguide](../../../.agents/skills/ts-styleguide/SKILL.md)
  и [tsx-styleguide](../../../.agents/skills/tsx-styleguide/SKILL.md). Для CSS —
  [postcss-styleguide](../../../.agents/skills/postcss-styleguide/SKILL.md), для обычного
  HTML — [html-styleguide](../../../.agents/skills/html-styleguide/SKILL.md).
  Профильные скиллы генератора, REST и SVG загружай по затронутой области.

В обоих приложениях действует строгий режим нового и изменяемого кода. Не используй
оговорку скилла «по умолчанию сохраняй стиль проекта» как разрешение игнорировать канон.
Соседний старый код, привычный паттерн, простота решения и зелёный build не являются исключением.
Локальный профиль уточняет разрешённые проектные решения, но не отменяет инварианты архитектуры.
При реальном конфликте норм не выбирай удобное исключение самостоятельно: сообщи блокер.

## Сверь подход, а не только внешний результат

Для каждой затронутой области выбери конкретные нормы из прочитанных документов и проверь:

1. **Архитектуру:** ответственность и ближайшего владельца, слой, необходимость границы,
   фасеты, колокацию, вложенность, публичный API, type-only и динамические зависимости,
   отсутствие циклов и совместимость транзитивного графа со средой.
2. **Создание компонентов:** обязательный запуск генератора для нового TSX, верный шаблон,
   адаптацию props, JSDoc, DOM, стилей и фасета; системные исключения — по ответственности,
   а не по имени файла. В проекте используется `template-generation-ru`.
3. **Прикладные решения:** способы работы с формами, состоянием, REST SDK, доменными
   адаптерами, GET/SWR и mutations, маршрутами, ошибками и UI-состояниями по своему reference.
   Ищи самописную параллельную реализацию или обход принятого инструмента, а не только ошибки API.
4. **Каноны кода:** TypeScript, подготовку данных и JSX, типы props, предикаты, декомпозицию,
   хуки, документирование, CSS Modules, тему и адаптивность по соответствующим стайлгайдам.
   Проверяй их фактически, даже если ESLint не содержит подходящего правила.
5. **Next.js:** серверную и клиентскую части, первоначальные данные, SSR и гидратацию,
   кеширование и обновление проекций, область жизни состояния и локальную границу авторизации.
   Не требуй миграции браузерной Bearer-сессии на cookie или введения новых фасетов
   только потому, что такие варианты описаны в общем скилле.
6. **Проверки:** требуемую архитектурную, сценарную и визуальную сверку, а для затронутых
   серверных границ — production-поведение, HTML/RSC и гидратацию. Зелёные lint, typecheck
   и build не заменяют эти доказательства и не доказывают соблюдение reference.

Список направляет чтение, но не заменяет сами скиллы. Не проверяй только перечисленные здесь
примеры, если затронута другая область reference. Не придумывай отсутствующие в нём запреты.

## Отдельно проверь подтверждение процесса

Запроси доступные материалы исполнения: применённые разделы скиллов, выбранного владельца,
UI/UX-решение при изменении интерфейса, команды генерации с каталогом запуска, результатом
и созданными путями, а также результаты обязательных проверок для проверяемого состояния.

Структура TSX сама по себе не доказывает запуск генератора. Отсутствие команды в diff
также не доказывает ручное создание. Если подтверждение не предоставлено, отметь
«процесс не подтверждён» и запроси материал у основного агента. Не выдумывай историю действий
и не перегенерируй компонент ради получения доказательства задним числом.

Указание исполнителем имени скилла не доказывает применение нормы: сопоставь его решение
с конкретным правилом и фактическим кодом. Подтверждение процесса и соответствие результата
проверяются раздельно; одно не заменяет другое.

## Обязательное заключение о соответствии

После замечаний включи компактную таблицу:

| Область | Норма: документ и раздел | Проверенный код / доказательство | Статус |
| --- | --- | --- | --- |

Используй статусы «соответствует», «нарушение», «не подтверждено», «не применимо».
Для неприменимости укажи причину. Не заполняй таблицу формальными галочками и не перечисляй
весь каталог скиллов: покажи реальные нормы затронутых областей и достаточное покрытие.
Для каждого нарушения добавь точное замечание по общему протоколу.

Нельзя заключать «референс соблюдён», пока остаются подтверждённые нарушения обязательных
норм или непроверенные применимые требования. Если блокер относится только к процессу,
так и раздели выводы: что подтверждено по коду и какое обязательство осталось неподтверждённым.
