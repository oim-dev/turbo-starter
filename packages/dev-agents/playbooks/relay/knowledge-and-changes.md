# Знания, документы и изменения требований

Роль: [оркестратор](../../src/orchestrator.md). Перед первым заполнением прочитай в
скилле Relay `references/guides/CONTENT.md`, а для выбранных сущностей —
`references/domain/PRODUCT.md` и `references/domain/DOCUMENTS.md`.

## Подготовь основания

Найди существующие записи и прочитай полный текст. Сохраняй исходное ТЗ и существенные
пояснения пользователя по мере анализа. Различай:

- **требование** — согласованное ожидаемое поведение;
- **факт** — наблюдение с источником и границами проверки;
- **предложение** — вариант, ещё не принятый пользователем или уполномоченным участником;
- **открытый вопрос** — существенное неизвестное, влияющее на решение.

Неизвестное фиксируй конкретно: что нужно выяснить, какое решение от этого зависит и
какую работу можно продолжить. Не заполняй пробелы требованиями, придуманными ради полноты.
Для существующего продукта сопоставляй намерение и поведение кода; расхождение сохраняй,
а не исправляй требование под существующую реализацию автоматически.

## Выбери владельца знания

| Знание                                                  | Запись Relay                   |
| ------------------------------------------------------- | ------------------------------ |
| Назначение, пользователи, цели, границы продукта        | Паспорт продукта               |
| Постоянная возможность и правила поведения              | Фича                           |
| Участник, условия, путь, ошибки и наблюдаемый результат | Сценарий одной фичи            |
| Ответственность программной части и взаимодействия      | Приложение                     |
| Вклад конкретного приложения в фичу/сценарий            | FI/SI                          |
| ТЗ, исследование, предложение, решение, инструкция      | Документ соответствующего типа |
| Изменение, которое необходимо выполнить                 | Задача и критерии              |
| Обоснование и организованный состав изменения           | План                           |
| Реально выполненные проверки и следующий шаг            | Комментарий задачи             |

Название — одна строка, `summary` — аннотация обычным текстом. Полные описания пиши
содержательным Markdown: поведение, условия, границы, ответственность, проверка.
Фраза «реализует фичу» не описывает обязательства приложения. Не копируй один контракт
во все реализации; общий смысл остаётся у фичи/сценария, собственный вклад — у FI/SI.

## Пройди продуктовую модель

1. Актуализируй паспорт в пределах известного.
2. Опиши фичи и сценарии. Каждый сценарий относится к одной фиче; переноса существующего
   сценария между фичами сейчас нет. Задача не становится сценарием по совпадению названия.
3. Определи реальные приложения. Не создавай фиктивное приложение ради группировки работы.
   До создания выбери осмысленные slug и prefix: позже они неизменяемы.
4. Для каждого приложения выбери FI и нужные SI. SI требует FI той же фичи в том же
   приложении; выбор FI не включает сценарии автоматически.
5. Опиши поведение, входы/выходы, взаимодействия, ошибки и проверку вклада приложения.
6. Перечитай сохранённое. До постановки ближайшей работы закрой существенные пробелы
   либо выдели исследование, которое позволит их закрыть.

Снятие реализации из состава сохраняет адрес и существующие ссылки, но исключает её
из активной готовности. Снятие FI требует снять и её SI. Не используй снятие участия
как способ получить готовность без согласованного пересмотра требований.

## Документы и решения

Используй библиотеку сразу, не откладывай её до конца анализа. Тип выбирается по смыслу:
`specification`, `description`, `rules`, `instruction`, `proposal`, `decision`, `research`.
Состояния: `draft`, `active`, `archived`; тип и состояние независимы.

- До создания ищи существующий документ и обновляй его при сохранении того же знания.
- Предложение сохраняй как `proposal`; принятие — явное изменение содержания и типа
  в `decision`, обычно с состоянием `active` и указанным основанием решения.
- Прикрепляй один документ к нужным сущностям через `document link`: `references`
  обозначает материал для чтения, `documents` — описание сущности. Объясни назначение связи.
- Ссылка в Markdown не создаёт прикрепления. Выбор родителя не включает детей.
  Этап плана и критерий задачи не являются самостоятельными целями документа.
- Устаревшее знание можно архивировать с понятным актуальным источником. Архивирование
  сохраняет адрес; удаление — отдельное действие со своими ограничениями.
- После записи прочитай документ и его отношения. Переданный массив при update может
  заменить весь набор, поэтому не передавай частичный список как добавление.

Для большого материала допустимо поручить исследователю подготовку черновика. Выдай
вопрос, источники, критерии полноты, предполагаемого владельца и формат результата.
По умолчанию сам проверь черновик и сохрани его. Если разрешена прямая запись воркером,
задай конкретный документ и поля, например создание `research/draft`; изменение задачи,
принятие решения и завершение работы этим не разрешаются.

## Требования изменились во время исполнения

1. Выясни, что именно изменил пользователь и входит ли новая работа в поручение.
2. Сохрани новое требование у канонического владельца, основание решения и открытые вопросы.
3. Прочитай связанные реализации, задачи, планы и прикреплённые документы. Используй
   отношения для поиска влияния, затем полные тексты; граф сам не доказывает полный объём.
4. Определи, какие результаты остаются верными, что нужно переработать и что потеряло смысл.
5. Уточни описания и критерии открытых задач, реальные зависимости и состав открытого плана.
   Отдельный объём вырази новой задачей. Технической работе необязательна продуктовая цель.
6. Сообщи затронутым исполнителям изменение цели. При конфликте с текущей правкой
   согласуй остановку/передачу и проверь уже созданный результат до нового поручения.
7. Повтори относящуюся к изменению приёмку и сохрани новые основания.

**Текст требования не сбрасывает готовность автоматически.** Для новой работы нужна задача
либо осознанное возвращение прежней задачи в работу. Изменение текста критерия сбрасывает
его отметку; в `done` критерии не редактируются — сначала верни задачу в работу.

После закрытого плана новый объём обычно оформляй новой задачей и новым/открытым планом.
Если прежняя работа фактически была не завершена, допустимо явно переоткрыть её задачу:
тогда проверь влияние на прежние планы и релизы, сохранённые статусы которых не изменятся.
Подробности — [приёмка и доработка](acceptance-and-rework.md).
