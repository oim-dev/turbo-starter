# Начало, продолжение и передача состояния

Роль: [оркестратор](../../src/orchestrator.md). Этот сценарий применяется перед первым
обращением к данным в сессии и при продолжении после паузы.

## 1. Установи контекст

Определи корень сопровождаемого проекта, цель пользователя и разрешённый этап работы:
исследование, варианты, план, реализация или выпуск. Проверь рабочую копию и текущие
процессы в затронутой области. Наличие папок, навыков и профилей не означает готовность
приложения, базы Relay или агентского инструментария.

Загрузи `relay` и используй его `scripts/diagnose.mjs`:

```sh
node "<абсолютный-каталог-скилла>/scripts/diagnose.mjs" --root "<корень-проекта>"
```

Подставь фактические пути. Диагностика read-only; exit 0 означает выполнение диагностики,
а не готовность всех компонентов. Прочитай состояния `configuration`, `server` и
рекомендации `next`. Рекомендации подключения MCP применимы только при порученном MCP.
Для деталей читай в скилле `references/guides/GETTING_STARTED.md` и нужный раздел
`references/interfaces/CONFIGURATION.md`.

## 2. Выбери существующее подключение

- Проверь local-конфиг, workspace, явные параметры и окружение, включая конфиги выше cwd.
  Подключение HTTP может существовать без локальной `.relay`.
- В workspace явно сохраняй `--project` во всех предметных командах. При нестандартном
  расположении сохраняй `--config`; при HTTP — проверенный URL. Не выбирай проект по
  похожему названию задачи: ключи уникальны только внутри проекта.
- Подтверди чтением конфигурации и идентичности проекта:

```sh
npx @oim-dev/relay-cli config get
npx @oim-dev/relay-cli project get
```

Для workspace или нестандартного подключения добавь установленные параметры. Сверь
`projectId`, имя и фактические пути/регистрацию с поручением. При доступном прежнем адресе
прочитай известную запись и сравни её идентичность. Ошибка, неполная `.relay` и
недоступный Server требуют [восстановления](recovery.md), а не `init`.

Если база действительно отсутствует, согласуй инициализацию, если она ещё не поручена.
После согласия выполни `npx @oim-dev/relay-cli init` из корня и повтори чтение.
Не создавай демонстрационные задачи для проверки соединения. Отсутствие подключения
обозначь как незавершённую настройку памяти; не заявляй, что результаты уже сохранены в Relay.

## 3. Подготовь интерфейс человека

Используй подходящий уже работающий Server либо запусти свой через
`npx @oim-dev/relay-server --open` по руководству скилла. Проверь API и выбранный проект,
а не только занятость порта. Для local CLI прямой доступ к базе не отменяет Web.
При занятом порте выбери свободный и согласуй фактический URL клиентов.

Сообщи пользователю кликабельную ссылку на Web и как поддерживается процесс:
собственная долгоживущая сессия или существующий сервер. Не обещай переживание процесса
после завершения инструмента, если среда этого не обеспечивает. Не останавливай чужой Server.
Прямые ссылки на сущности составляй по `references/interfaces/WEB-ROUTES.md` скилла,
из реальных slug и ключей, а не по предполагаемому маршруту.

Синтаксис первого нового действия проверь через `--help`. Скилл и checkout Relay могут
быть новее опубликованного CLI; недоступную команду обозначь, а не обходи прямой записью JSON.

## 4. Выбери маршрут работы

### Новая память или новый объём

Прочитай паспорт и обзор продукта, затем исходное ТЗ и относящиеся документы:

```sh
npx @oim-dev/relay-cli product overview
npx @oim-dev/relay-cli product get
```

Пустой паспорт ещё не означает отсутствия продукта. Существующий код изучается как
свидетельство текущего устройства, не как безусловное требование. Затем переходи к
[сбору знаний](knowledge-and-changes.md). Ограничь анализ ближайшим поручением;
исправление конкретного бага не требует заново описывать весь продукт.

### Продолжение известной работы

1. Найди нужные задачи и планы; прежде создания проверь существующие записи.
2. Прочитай полные постановки, критерии, комментарии, требования и материалы.
   Для обсуждения `comment list` даёт карточки; нужный текст открывай через `comment get`.
3. Прочитай состав открытого плана, зависимости и текущую готовность. Дочитай нужные страницы.
4. Сопоставь сохранённые результаты с фактическими файлами, проверками и доступными
   сессиями исполнителей. `in-progress` не доказывает, что старый воркер ещё работает.
5. Для живого воркера продолжай координацию, не выдавай дубликат. Если он завершился,
   потерян или недоступен, проверь частичный результат и зафиксируй следующий шаг.
   Самостоятельную цель передай новой сессии с актуальным контекстом.
6. Перед любой записью перечитай ревизию. Идентификатор старого запуска не подтверждает
   состояние задачи или право перезаписать изменившуюся запись.

## 5. Перед паузой

Сохрани в задаче существенный промежуточный результат: готовое, проверки, незавершённое,
блокер и конкретное продолжение. Устойчивое решение размести у владельца знания.
При необходимости добавь адреса активных поручений, владельцев файлов/ресурсов и артефактов,
чтобы следующий оркестратор мог выяснить их судьбу. Не записывай журнал опросов агентов.

Пользователю передай проект, ссылки на текущие задачу/план и материалы, ограничения,
ближайшее действие и собственные оставшиеся процессы. Продолжение должно опираться на
Relay и проверяемые артефакты, а не на обязательное сохранение этой беседы.
