# Проектные агенты

Приватный workspace-пакет `@repo/dev-agents` хранит единые исходники ролей и
генерирует определения для OpenCode, Claude Code и Codex. Главная роль —
[`orchestrator-agent`](src/orchestrator.md): сам ведёт память проекта в Relay, запускает
профильных воркеров в фоне и принимает результаты.

## Роли и источники

| Роль                 | Назначение                                                      | Исходник                               |
| -------------------- | --------------------------------------------------------------- | -------------------------------------- |
| `orchestrator-agent` | Требования, документы, задачи, планы, приёмка и выпуски в Relay | [orchestrator.md](src/orchestrator.md) |
| `frontend-agent`     | React SPA, Unit Architecture, UI/UX и клиентские проверки       | [frontend.md](src/frontend.md)         |
| `engineering-agent`  | Каркас, пакеты, интеграции, инструменты и сборка                | [engineering.md](src/engineering.md)   |
| `research-agent`     | Исследования и порученная подготовка объёмных документов        | [research.md](src/research.md)         |
| `qa-agent`           | Независимая проверка и воспроизведение дефектов                 | [qa.md](src/qa.md)                     |

[Manifest](src/manifest.json) версии 1 задаёт имя `orchestrator` и список `agents`
с полями `name`, `kind`, `description`, `prompt`. Нужен один оркестратор; остальные —
воркеры. `prompt` указывает на Markdown относительно `src`.

Каждое тело роли целиком, с одинаковым форматированием, попадает во все три среды.
Пути в профилях считаются от корня репозитория. Сборщик не вклеивает общие `AGENTS.md`
или весь скилл в каждый профиль: роли явно требуют прочитать применимые инструкции,
если их ещё нет в контексте.

- [Корневой AGENTS.md](../../AGENTS.md) — общие правила для всех сессий; резервный выбор
  роли оркестратора относится только к главной сессии без именованного профиля.
- [Правила пакета](AGENTS.md) — сопровождение источников, сборщика и выходов сред.
- [Правила Web](../../apps/web/AGENTS.md) — обязательные frontend-требования для разработки
  и QA. Полный профиль и локальные правила перенесены из Relay с адаптацией источников.
- [README Web](../../apps/web/README.md) — подготовка пока не созданного приложения;
  наличие инструкций и браузерного конфига не означает наличия React-пакета.

## Память и фоновое исполнение

Оркестратор загружает `relay` и работает через `npx @oim-dev/relay-cli` с читаемым выводом.
Он сам сохраняет требования и решения, ведёт задачи/планы, фиксирует приёмку и сведения
о поставке. Воркеры по умолчанию читают адресный контекст и возвращают результат.
Для тяжёлого исследования или большого документа можно выдать отдельное поручение
подготовки; сохранение и принятие обычно выполняет оркестратор.

**Каждое поручение запускается в фоне, когда среда поддерживает такой режим, даже
единственное.** Готовые независимые поручения запускаются параллельно. Общие файлы,
контракты, данные и процессы получают согласованного владельца. Пока исполнители
работают, оркестратор продолжает вести Relay и готовить следующие шаги.

Нативные инструменты запускаются из главной сессии. У воркеров нет обязанности
создавать ещё одну команду или самостоятельно вести статусы. Ограничения роли —
рабочий протокол; сборщик не настраивает отдельные ACL, sandbox, квоты или модели.

## Сборка

Из корня проекта:

```sh
pnpm install
pnpm setup
pnpm run agents:check
```

У пакета единственная инструментальная зависимость — закреплённый Prettier для стабильного
форматирования выходов. Сборка приложений не нужна. Общий `pnpm build` также включает пакет;
его Turbo-задачи `build` и `check` выполняются без зависимостей задач и без кеша, поскольку
выходы лежат в корне проекта. Генерируемые файлы исключены из Git, поэтому в CI
сначала выполняйте `pnpm setup`, затем `pnpm run agents:check`.

`pnpm setup` восстанавливает скиллы из `skills-lock.json` и собирает профили агентов.
Для повторной сборки только профилей используйте `pnpm run agents:build`.

Доступны `--help`, `--root <каталог>` и `--format json`. Например:

```sh
pnpm --silent run agents:check --format json
node packages/dev-agents/scripts/check.mjs --root /путь/к/проекту
```

Относительный `--root` считается от места вызова пользователя, в том числе через pnpm.
В другом корне ожидается та же структура источников и локальных инструкций.

### Генерируемые файлы

| Среда       | Выходы                                         | Главная сессия и воркеры                                                                     |
| ----------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| OpenCode    | `.opencode/agents/*.md`, `opencode.json`       | `default_agent: orchestrator-agent`, `primary` у главного, `subagent` у воркеров             |
| Claude Code | `.claude/agents/*.md`, `.claude/settings.json` | Настройка `agent`, `model: inherit`; `background: true` только у воркеров                    |
| Codex       | `.codex/config.toml`, `.codex/agents/*.toml`   | Главный в `developer_instructions`, самостоятельные TOML воркеров, `[agents] enabled = true` |

Для пяти ролей получается **17 выходных файлов и `agents-lock.json`**. Они создаются
локально и исключены из Git. В Git хранятся исходники сборщика и `skills-lock.json`.
Локальный lock содержит владельца `@repo/dev-agents`
и SHA-256, без времени генерации. Модель наследуется от пользовательской среды;
реальное поведение также зависит от её runtime-настроек.

### Владение и сопровождение

1. Меняйте профиль в `src`, сценарий в `playbooks/relay`, общие правила в нужном `AGENTS.md`.
   При изменении состава обновляйте manifest и таблицу команды главного профиля.
2. Форматы выходов меняйте в [adapters.mjs](scripts/adapters.mjs). Управляемая конфигурация
   принадлежит сборщику целиком: ручные дополнительные поля нужно перенести в источник
   адаптера, а не ожидать произвольного слияния при следующей сборке.
3. После готовности всех источников один исполнитель запускает build → check.
   Одновременные сборки не поддерживаются.
4. `check` только читает: сравнивает ожидаемые выходы/lock, проверяет конкретные пути
   `AGENTS.md` и необходимые локальные Markdown-ссылки. Якоря, внешние URL и установленное
   содержимое skills этим не проверяются. Семантика ролей оценивается при ревью.

Первый build требует свободных выходных путей. Даже совпадающий файл без владения в lock
считается чужим. Посторонние файлы за пределами lock сохраняются. Ручные изменения
управляемого файла не затираются: сначала перенесите нужный смысл в источник, сохраните
изменённый файл вне выходного пути. Генерируемые файлы не хранятся в Git.
Удаление роли убирает только её прежние неизменённые управляемые выходы.

Перед записью проверяется весь набор и коллизии. Публикация атомарна для одного файла,
не всего набора; lock записывается последним. После прерывания выполните check,
проверьте происхождение новых файлов без lock и сохраните их перед повторной сборкой.

## Подключение и короткая проверка

1. Установите проектные skills по [инструкции](../../docs/development/skills.md).
   Они не входят в генерируемые профили и не хранятся в Git. Для воспроизводимого обновления
   фиксируйте источник скилла на commit SHA по той же инструкции.
2. Выполните build/check и запустите клиент из корня проекта. После изменения конфигураций
   **перезапустите OpenCode**; уже работающие исполнители продолжают старое поручение.
   При первом добавлении каталога агентов начните также новые сессии Claude Code и Codex.
   Проектные настройки Codex требуют доверенного проекта.
3. Убедитесь, что главным выбран `orchestrator-agent`, а четыре воркера доступны.
4. Дайте короткое read-only поручение, например: «Поручи research-agent в фоне назвать
   фактические корневые scripts; пока он работает, объясни, где определены правила приёмки».
   Проверьте фактический фоновый запуск, правильную роль и результат. Если среда не умеет
   фон, оркестратор должен обозначить ограничение и использовать доступное делегирование.
5. Перед работой с памятью пройдите стартовый сценарий: диагностика, проверка проекта,
   при необходимости согласованная инициализация, Server и ссылка на Web. Сам пакет
   агентов не создаёт базу Relay и не подключает MCP.

Сборки, проверки актуальности/ссылок и короткого делегирования достаточно для сопровождения
пакета. Отдельная система тестов профилей не создаётся. Принятие JSON/TOML клиентом
не подтверждает выполнение инструкций моделью; в результате проверки указывайте
фактическую версию клиента, наблюдаемое поведение и непроверенное.
