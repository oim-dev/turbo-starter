# Публичные и приватные данные SWR

SWR обслуживает приватные GET после подтверждения браузерной сессии и публичные GET, которым требуется обновление
после гидратации. Если для публичных данных достаточно серверного дерева при переходе или записи, не добавляй хук
и Provider. Основной процесс описан в [получении данных](../application/data-fetching/README.md).

## Публичный контракт

Домен публикует `useGet...` через `client.ts`. Хук вызывает внутренний браузерный адаптер, а тот — настроенный
API-клиент из `infra/<api>/browser`.
Общий построитель ключа публикуй через `index.ts`, если он нужен серверу: он не импортирует хук и транспорт.
Для публичного ключа используй устойчивый префикс ресурса и все параметры; для приватного добавь безопасный идентификатор
пользовательской области, например `['private', scopeId, 'account']`. `scopeId` различает поколения сессии,
а не только пользователей. JWT и его производные значения в ключ не входят.

SWR используется только для GET. Приватная запись выполняется браузерной доменной операцией.
Независимая от JWT серверная запись выполняется через Server Action вне SWR.
`useSWRMutation` в этом профиле не вводится как второй способ записи.

## Публичный первоначальный результат

Только для публичных данных передай серверный результат как `fallbackData` с тем же предметным контрактом одному потребителю.
Для нескольких потребителей используй `fallback` в клиентском `SWRConfig`; ключ-кортеж на сервере сериализуй через
разрешённый в RSC `unstable_serialize` из `swr`. Не импортируй сервером обычный хук `useSWR` или `useSWRConfig`.

Значения `SWRConfig`, содержащие функции, создавай внутри клиентского Provider. Например, `provider: () => new Map()`
нельзя передать как обычное свойство из Server Component. Не создавай приватный `Map` на уровне модуля.

Для свежего серверного снимка по умолчанию задай `revalidateOnMount: false`, чтобы не повторять запрос сразу после SSR.
Применяй это только когда есть данные **для текущего ключа**. Новому ключу без исходных данных запрос необходим.
Настройки обновления по фокусу, восстановлению связи и интервалу задавай по требованиям актуальности.

Не используй один `fallbackData` без привязки к ресурсу после смены ключа: прежняя сущность не становится
первоначальным значением новой. `isLoading` при начальных данных не доказывает их отсутствие; показывай серверный результат,
а повторную загрузку обозначай отдельно через `isValidating`.

## Приватный первоначальный запрос

На сервере и при первом клиентском отображении статус сессии `unknown`, ключ равен `null`, показана нейтральная
заглушка. Сервер не передаёт приватные `fallback`, `fallbackData` или свойства с данными пользователя.

После монтирования домен авторизации восстанавливает JWT и подтверждает сессию через backend. Только после этого
хук получает активный `scopeId` и выполняет первый GET. Не переноси публичное `revalidateOnMount: false` на приватный
ключ без данных: его первый запрос необходим. Обновление и права на каждый запрос контролирует backend.

## Обновление и сессия

После записи используй `mutate` из `useSWRConfig()` **текущего** Provider. Глобальный `mutate` не обслуживает автоматически
изолированный Provider. Обновляй подтверждённым предметным результатом либо повторным GET.

Если публичный ресурс представлен одновременно в RSC и SWR, явно обнови обе проекции по [карте кешей](../application/data-fetching/caching.md).
Изменение свойства `fallback` при `router.refresh()` не является гарантированной перезаписью уже заполненного SWR-кеша.

Приватный Provider создаёт отдельный кеш на каждое поколение сессии и перемонтируется при смене безопасного `scopeId`.
Хуки не запускают запрос без подтверждённой области; используй `null` key. При выходе сначала отключи их и закрой
приватный UI, затем очисти старую область. Сохраняемый layout должен получить явный сигнал её смены.
Не используй `keepPreviousData` между сессиями. Поздние ответы остаются в недоступной старой области, а обработчики
и внешние записи дополнительно проверяют поколение по [состоянию](../application/state-management/README.md#приватная-область-сессии).

## Ошибки

Тип `error` соответствует всем фактически возможным исключениям fetcher. Если адаптер не закрывает канал ошибок
полностью, используй `unknown` с проверкой, а не обещай только один класс предметной ошибки.
Для начальной ошибки без данных покажи безопасное состояние с повтором. Для фоновой ошибки при имеющихся данных
сохрани допустимый снимок и сообщи о проблеме по сценарию.

Публичный свежий снимок не вызывает лишний GET сразу после SSR. Приватный GET не начинается до подтверждения сессии,
затем выполняется без серверного начального результата. Смена ключа, фоновое обновление и запись не смешивают сессии;
после выхода или повторного входа поздний ответ не возвращает старые данные.
