# SWR поверх серверных исходных данных

SWR нужен для GET-данных, которые должны обновляться после гидратации. Если достаточно серверного дерева при
переходе или записи, не добавляй хук и Provider. Основной процесс описан в [получении данных](../application/data-fetching/README.md).

## Публичный контракт

Домен публикует `useGet...` через `client.ts`. Хук вызывает браузерный адаптер, а тот — настроенный API-клиент.
Общий построитель ключа публикуй через `index.ts`, если он нужен серверу: он не импортирует хук и транспорт.
Для публичного ключа используй устойчивый префикс ресурса и все параметры; для приватного добавь безопасный идентификатор
пользовательской области, например `['private', scopeId, 'account']`. Токен доступа в ключ не входит.

SWR используется только для GET. Запись выполняется обычной доменной операцией или Server Action вне SWR;
`useSWRMutation` в этом профиле не вводится как второй способ записи.

## Передача первоначального результата

Для одного потребителя передай серверный результат как `fallbackData` с тем же предметным контрактом.
Для нескольких потребителей используй `fallback` в клиентском `SWRConfig`; ключ-кортеж на сервере сериализуй через
разрешённый в RSC `unstable_serialize` из `swr`. Не импортируй сервером обычный хук `useSWR` или `useSWRConfig`.

Значения `SWRConfig`, содержащие функции, создавай внутри клиентского Provider. Например, `provider: () => new Map()`
нельзя передать как обычное свойство из Server Component. Не создавай приватный `Map` на уровне модуля.

Для свежего серверного снимка по умолчанию задай `revalidateOnMount: false`, чтобы не повторять запрос сразу после SSR.
Применяй это только когда есть данные **для текущего ключа**. Новому ключу без исходных данных запрос необходим.
Настройки обновления по фокусу, восстановлению связи и интервалу задавай по требованиям актуальности.

Не используй один `fallbackData` без привязки к ресурсу после смены ключа: прежняя сущность не становится
первоначальным значением новой. `isLoading` при начальных данных не доказывает их отсутствие; показывай серверный результат,
а повторную загрузку обозначай отдельно через `isValidating`.

## Обновление и сессия

После записи используй `mutate` из `useSWRConfig()` **текущего** Provider. Глобальный `mutate` не обслуживает автоматически
изолированный Provider. Обновляй подтверждённым предметным результатом либо повторным GET.

Если экран одновременно показывает RSC и SWR-проекцию, явно обнови обе по [карте кешей](../application/data-fetching/caching.md).
Изменение свойства `fallback` при `router.refresh()` не является гарантированной перезаписью уже заполненного SWR-кеша.

Приватный Provider перемонтируется при смене безопасного `scopeId`. Хуки не запускают запрос без подтверждённой
области; используй `null` key. После выхода не оставляй предыдущие данные под ключом нового пользователя.
Постоянно сохраняемый layout должен получить явный сигнал смены этой области.

## Ошибки

Тип `error` соответствует всем фактически возможным исключениям fetcher. Если адаптер не закрывает канал ошибок
полностью, используй `unknown` с проверкой, а не обещай только один класс предметной ошибки.
Для начальной ошибки без данных покажи безопасное состояние с повтором. Для фоновой ошибки при имеющихся данных
сохрани допустимый снимок и сообщи о проблеме по сценарию.

Проверь отсутствие лишнего GET сразу после SSR, смену ключа, фоновое обновление, запись, выход и поздний ответ старой сессии.
