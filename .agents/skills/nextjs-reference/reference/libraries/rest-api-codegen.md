# REST-клиент в двух средах

Перед реализацией загрузи `rest-api-codegen-ru`. Для браузерной авторизации используй его рецепт JWT, для серверной
части — правила разделения клиентов и операций по средам. Рецепт серверной cookie-сессии не является выбором этого
профиля: [авторизация](../application/authentication/README.md) остаётся браузерной. Профильный skill владеет CLI,
контрактом `HttpClient`, ручными операциями и исправлениями генерации; этот документ задаёт размещение и ограничения.

## Размещение

```text
infra/service-api/
├── server.ts                        # только для публичных серверных вызовов
├── browser.ts                       # браузерный транспорт, в том числе JWT
├── service-api.server.ts
├── service-api.browser.ts
├── generated/
└── operations/                     # только ручные операции или исправления
```

Создавай только нужные части. `client.ts` нужен лишь при собственном React-контракте API-модуля, а не вместо
браузерного транспорта. Общие типы при реальных потребителях публикуй через универсальный `index.ts`.

Клиенты используют общие типы и операции, но разные адреса и правила авторизации. Не экспортируй настроенные
клиенты из общего `index.ts`. Прямые импорты generated-операций разрешены внутри владельца API; домен использует
фасет API-модуля, экран — фасет домена.

## Настройка

1. Найди OpenAPI, общий SDK или существующий клиент. Не выдумывай операции и не создавай второй клиент того же сервиса.
2. Закрепи версию генератора и команду проекта. `generated/` целиком принадлежит генератору.
3. Собери нужный набор операций через `createApiClient`; не импортируй полное дерево ради одного метода.
4. Серверную реализацию пометь `server-only`. Она обращается только к публичным данным, не читает браузерный JWT
   и не получает пользовательскую авторизацию из cookie. Адрес сервиса бери из серверной конфигурации.
5. Браузерную реализацию пометь `client-only`. Импорт не читает `localStorage`, не запускает сеть и совместим с SSR.
   Использование транспорта начинается после монтирования или из клиентского события.
6. В `onRequest` добавляй актуальный JWT только к защищённым операциям известного backend. Способ получения токена
   передай техническому клиенту через настройку или существующее техническое хранилище; `infra` не импортирует домен
   авторизации. Не сохраняй JWT в общих заголовках при создании клиента.
7. Приватные браузерные запросы явно используют `cache: 'no-store'`. Проверь сигнатуры `RequestParams`, перехватчиков
   установленной версии и фактический уходящий `RequestInit`. Заголовки ответа backend согласуются по
   [кешированию](../application/data-fetching/caching.md).
8. В домене преобразуй DTO и ошибки до возврата компоненту или записи в SWR. Приватные вызовы не начинаются
   до подтверждения сессии; вход и сама проверка сессии используют отдельный контракт.

`credentials: 'include'` не заменяет `Authorization: Bearer`. Не вводи cookie-аутентификацию или приватный прокси
Next.js вместо согласованного браузерного доступа к backend. Для другого origin проверь разрешение `Authorization`
и origin приложения в CORS backend.

Не пересылай JWT в сторонние адреса, URL, Server Actions или серверные обработчики. Серверный транспорт
не импортирует браузерную реализацию, а браузерный — серверную. Защита `client-only` не отменяет SSR клиентского дерева.

## Кеш и параметры Next.js

Не считай произвольный `fetch`-клиент автоматически совместимым с расширениями Next.js. Не обходи типы приведением
`as` ради `next.tags`. Базовый вариант — некеширующий публичный серверный транспорт и явная доменная кеширующая
операция по [кешированию](../application/data-fetching/caching.md). Приватного серверного транспорта в профиле нет.

Если существующий публичный транспорт поддерживает расширенный `fetch`, проверь, что опции доходят без потери до
серверного `fetch`, и сохрани одно место политики. Не накладывай два независимых времени жизни кеша.

## Ошибки, повтор и смена сессии

Транспорт отвечает за тайм-аут, отмену, ограниченный повтор и технический ответ. Домен распознаёт ожидаемый исход;
публичный маршрут решает о `notFound`/`redirect`. Не добавляй SWR, Zustand или навигацию в транспорт.
Для терминального Bearer `401` сохрани внутреннюю связь ошибки с поколением сессии и отклонённым токеном,
чтобы домен применил [правила завершения сессии](../application/authentication/README.md#выход-смена-сессии-и-поздние-ответы).
Эти данные не логируются и не входят в публичную ошибку.

Не повторяй запись после сетевого сбоя без идемпотентного контракта. Повтор или обновление JWT старого запроса
не может использовать уже другую сессию: проверь захваченное поколение до повторного вызова и принятия результата.

## Проверка

Публичное серверное чтение не содержит пользовательского JWT. Приватный предметный запрос содержит Bearer и
выполняется только в активной сессии; проверка и установление самой сессии соблюдают отдельный контракт.
`no-store`, отмена, `401`/`403`/`404` и неизвестный ответ соответствуют контракту.
Две сессии не смешивают заголовки и результаты; серверный код не попадает в клиентскую сборку.
