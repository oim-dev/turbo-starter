# REST-клиент в двух средах

Перед реализацией загрузи `rest-api-codegen-ru` и прочитай его рецепт Next.js/SSR. Он владеет CLI, контрактом
`HttpClient`, ручными операциями и исправлениями генерации. Этот документ задаёт интеграцию с архитектурой приложения.

## Размещение

```text
infra/service-api/
├── server.ts
├── client.ts                       # только при реальных браузерных вызовах
├── service-api.server.ts
├── service-api.client.ts
├── generated/
└── operations/                     # только ручные операции или исправления
```

Серверный и браузерный клиенты используют общие типы/операции, но разные адреса и правила авторизации. Не экспортируй
оба из `index.ts`. Прямые импорты generated-операций разрешены внутри владельца API; потребители используют его фасет.
Домен получает технический API, экран — только API домена.

## Настройка

1. Найди OpenAPI, общий SDK или существующий клиент. Не выдумывай операции и не создавай второй клиент того же сервиса.
2. Закрепи версию генератора и команду проекта. `generated/` целиком принадлежит генератору.
3. Собери нужный набор операций через `createApiClient`; не импортируй полное дерево для одного метода.
4. Серверную реализацию пометь `server-only`. Адрес внешнего сервиса бери из серверной конфигурации.
5. Используй фабрику клиента для запроса, если экземпляр хранит контекст пользователя. Общий неизменяемый клиент
   допустим только если `onRequest` читает текущую сессию перед каждым вызовом и не мутирует общее состояние.
6. Явно установи `cache: 'no-store'` для приватных запросов. Проверь реальные сигнатуры `RequestParams` и перехватчиков транспорта
   установленной версии, затем проверь уходящий `RequestInit` интеграционным тестом.
7. Для браузерного транспорта используй same-origin URL и cookie браузера. Не читай `HttpOnly` cookie из JavaScript.
8. Преобразуй DTO и ошибки в домене до возврата компоненту или записи в SWR.

`credentials: 'include'` на сервере не подставляет cookie входящего запроса. Передавай разрешённое значение через
`onRequest` либо контекст фабрики. Для same-origin браузерных вызовов достаточно стандартной политики; для согласованного
cross-origin cookie API требуется `include` и соответствующий CORS сервиса.

Настроенный под запрос экземпляр не сохраняй в общем кеше или модуле. Не пересылай все входные заголовки: адресат,
набор заголовков и cookie определяются контрактом интеграции.

Транспорт не импортирует домен авторизации. Домен может получить сессию и передать ограниченный контекст фабрике
клиента. Если `onRequest` читает cookie самостоятельно, он только добавляет предусмотренное контрактом значение;
проверка действительности сессии и предметных прав остаётся в домене.

## Кеш и нестандартные параметры Next.js

Не считай произвольный `fetch`-клиент автоматически совместимым с расширениями Next.js. Не обходи типы приведением
`as` ради `next.tags`. Базовый вариант — некеширующий транспорт и явная доменная кеширующая операция по
[кешированию](../application/data-fetching/caching.md).

Если существующий транспорт уже поддерживает расширенный `fetch`, проверь, что опции доходят без потери до
серверного `fetch`, и сохрани одно место политики. Не накладывай незаметно два независимых времени жизни кеша.

## Ошибки и повтор

Транспорт отвечает за тайм-аут, отмену, ограниченный повтор и технический ответ. Домен распознаёт ожидаемый исход;
маршрут решает о `notFound`/`redirect`. Не добавляй SWR, Zustand или браузерную навигацию в транспорт.
Не повторяй запись после сетевого сбоя, если неизвестно, была ли она применена, без идемпотентного контракта.

Проверь параллельные запросы двух сессий, no-store, отмену, 401/403/404 и неизвестный ответ. Убедись, что server-only
код не попадает в клиентский граф при производственной сборке.
