# Сессия и доступ

В новом приложении используй серверную сессию в `HttpOnly` cookie через принятый библиотечный или внешний механизм
авторизации. Не проектируй собственную криптографию сессии и не переносись с браузерной SPA на хранение токена в
`localStorage`: серверное открытие страницы не может прочитать это хранилище.

## Ответственность

- Домен авторизации владеет проверкой сессии, её безопасным представлением, входом и выходом.
- Инфраструктурный API-модуль добавляет нужные данные авторизации к запросу, но не выбирает страницу и не очищает UI.
- Предметная серверная операция проверяет доступ пользователя к запрошенному ресурсу.
- `page.tsx` или маршрутная граница переводит предметный исход в переход или состояние страницы.
- Клиентский Provider получает только безопасные данные для отображения; он не доказывает наличие доступа.

## Чтение сессии

1. В серверной реализации используй `await cookies()` или API принятой библиотеки.
2. Проверь подпись/существование, срок жизни и фактическую действительность сессии согласно её контракту.
3. Верни минимальное предметное представление: идентификатор пользователя, нужное имя и разрешения для UI.
4. Не кешируй результат между запросами; React `cache` допустим для повторного чтения в одном серверном отображении.
5. Не передавай токены доступа и обновления или исходную запись сессии в RSC-свойства, SWR-ключи и HTML.

Наличие cookie не означает подтверждённую сессию. У серверного HTTP-клиента нет браузерного cookie-хранилища:
пересылай только предусмотренное контрактом значение в известный сервис. Не сохраняй его в общих изменяемых заголовках.

## Где проверять доступ

Проверка в layout удобна для общего интерфейса, но недостаточна для защиты. Layout может сохраняться между
переходами, а дочерние серверные чтения выполняются независимо. Проверяй доступ внутри каждой защищённой серверной
операции, включая вызовы из страницы, Action, Route Handler и метаданных.

`proxy.ts` в Next.js 16 пригоден для раннего перенаправления или маршрутизации. Он не заменяет проверку сессии и
прав у данных. Не добавляй обращение к основному API на каждый статический ресурс через слишком широкий matcher.

Недоступный объект может давать 403 либо скрываться как 404 по продуктовым правилам. Не определяй это различие
исключительно в UI. Не отправляй приватные данные клиенту с расчётом, что клиентский гард их скроет.

## Вход, обновление и выход

Cookie устанавливается и удаляется в Server Action или Route Handler до начала потока ответа. Server Component
читает сессию, но не обновляет cookie во время отображения. Ротацию сессии выполняй в поддерживаемой границе записи
принятой библиотеки, а не скрытым побочным эффектом транспорта при чтении данных.

Для рабочей HTTPS-среды используй `HttpOnly`, `Secure`, согласованный `SameSite`, срок жизни и узкую область действия.
Разрешённый адрес возврата после входа проверяй: внешний `returnTo` не должен становиться произвольным перенаправлением.

При выходе:

1. Заверши сессию на сервере, если контракт поддерживает отзыв, и удали cookie с правильными атрибутами пути/домена.
2. Получи новое серверное дерево или выполни переход.
3. Пересоздай приватную область SWR и Zustand по безопасному идентификатору сессии/версии, чтобы поздний ответ старого
   запроса не заполнил кеш нового пользователя.

Удаление cookie через Action может обновить серверное дерево, но само по себе не очищает независимый кеш SWR и
не сбрасывает сохранённое клиентское состояние. Подробности — [состояние](../state-management/README.md).

Терминальный 401 интерпретирует вызывающий домен как отсутствие действующей сессии. Серверный транспорт не вызывает
браузерный выход из сессии и не изменяет общее хранилище. 401 операции входа может означать неверные данные и обрабатывается её
собственным контрактом. Не повторяй запись автоматически ради обновления токена без гарантии идемпотентности.

## Проверка

Проверь прямой URL без cookie, истёкшую сессию, доступ к чужому объекту, прямой вызов Action/Handler и выход с
возвратом назад. В двух независимых браузерных контекстах пользовательские данные и cookie не должны смешиваться.
