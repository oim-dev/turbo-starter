# Браузерная JWT-сессия и доступ

Базовая авторизация профиля — JWT в `Authorization: Bearer`: браузер восстанавливает сессию, а backend подтверждает её
действительность. Наличие сохранённого токена, его декодирование и клиентский статус не доказывают наличие доступа.
Не заменяй эту схему серверной cookie-сессией ради SSR и не создавай собственную криптографию JWT.

## Ответственность

- Домен авторизации владеет восстановлением, проверкой, входом, выходом и статусом сессии.
- Инфраструктурный API-модуль добавляет JWT перед защищённым запросом, но не выбирает маршрут и не очищает UI.
- Предметный домен преобразует ответ backend в модель и предусмотренные исходы операции.
- Backend проверяет действительность сессии и права на конкретные данные и операции при каждом защищённом вызове.
- Клиентский guard управляет отображением. Он не защищает API и не предотвращает выполнение Server Components.

## Восстановление и проверка

1. На сервере и при первом клиентском отображении используй статус `unknown` и нейтральную заглушку без приватных данных.
2. После монтирования начни поколение попытки восстановления и прочитай JWT через принятый механизм браузерного
   хранения. Чтение не выполняется при импорте модуля или во время отображения компонента.
3. Если токена нет, установи состояние гостя. Если он есть, вызови предусмотренную backend операцию проверки сессии.
   Этот запрос и вход являются частью установления сессии, а не приватными запросами, ожидающими её подтверждения.
4. Перед применением любого ответа сравни поколение попытки с текущим. Успех и ошибка завершённого поколения
   не изменяют JWT, статус, кеш или интерфейс.
5. Только подтверждённый backend результат переводит текущую сессию в `authenticated` и открывает её приватную область.
6. При отказе backend удали отклонённый токен и покажи состояние гостя. При временном сбое покажи ошибку проверки
   с повтором, не выдавая её ни за подтверждённую сессию, ни за доказанный выход.

Новый вход также начинает новое поколение и завершает прежнюю приватную область. Если успешный ответ входа
подтверждает сессию по контракту backend, он может сразу открыть новую область; иначе выполни проверку сессии.

Место хранения, срок жизни, восстановление после перезагрузки и обновление JWT определяются контрактом приложения
и backend. Не добавляй `localStorage`, сохранение в Zustand или запрос обновления токена по предположению. Если проект уже
использует `localStorage`, обрабатывай недоступное или повреждённое хранилище и учитывай доступ любого JavaScript
страницы к токену: защита от XSS обязательна.

## Граница сервера и браузера

Авторизационно-зависимые чтения, записи и подписки запускаются только браузером после проверки сессии.
Для них используй публичные браузерные операции домена и клиентские хуки по
[получению данных](../data-fetching/README.md). Вход, проверка, обновление и завершение сессии используют собственный
контракт, поскольку управляют самой сессией.

Next.js-сервер не использует браузерный JWT. Не передавай его в Server Action, Route Handler, URL или cookie
для обхода этого ограничения. Не создавай приватный прокси через Next.js. Браузер обращается к backend по согласованному
API; для другого origin backend должен разрешать нужный origin и заголовок `Authorization`.

JWT, сведения о сессии и приватные ответы не попадают в серверный HTML, metadata, RSC payload, свойства Server Components
и серверные начальные данные SWR. После загрузки в браузере приватные компоненты могут передавать предметные данные
друг другу внутри клиентского дерева. Не выводи токен в логи, телеметрию и публичные идентификаторы кеша.

На смешанной странице сервер загружает только публичную часть. Приватная область реализована клиентскими компонентами
с одинаковой начальной заглушкой по [правилам SSR](../rendering/README.md). Оборачивание серверного чтения клиентским
guard не делает это чтение приватным: сервер выполнит его до клиентской проверки.

## Выход, смена сессии и поздние ответы

1. Синхронно закрой приватный интерфейс и отключи новые защищённые запросы.
2. Заверши старую область сессии, удали её JWT, очисти приватные данные и черновики по
   [правилам состояния](../state-management/README.md). Отмени запросы и подписки, где это поддерживается.
3. Если backend поддерживает завершение сессии, уведомь его по принятому контракту. Ошибка этого запроса не возвращает
   локальный токен и старый интерфейс. Для уведомления допустимо временно удержать прежний токен внутри операции выхода.
4. Новую приватную область активируй только после подтверждения новой сессии. Даже повторный вход того же пользователя
   не переиспользует прежнее поколение. Обычное обновление JWT в той же сессии само по себе не меняет область кеша.
5. Не применяй успешные ответы, ошибки, результаты входа, проверки и обновления JWT к уже другой сессии.
   Одной отмены запроса недостаточно: сравни поколение перед изменением состояния.

Терминальный Bearer `401` после предусмотренного контрактом обновления токена интерпретирует вызывающий домен.
Он завершает только текущую отклонённую сессию: сравни поколение и токен запроса с актуальными значениями.
Поздний `401` старой сессии не завершает новую. `401` входа может означать неверные данные, а временный сбой обновления
не доказывает потерю сессии. Транспорт не импортирует домен авторизации, SWR или роутер.
Не повторяй запись автоматически ради обновления токена без гарантии идемпотентности backend.

## Проверка

Ожидаемые результаты собраны в [качестве](../quality/README.md#приёмка-сценария): до проверки нет приватных запросов
и содержимого, backend отклоняет неразрешённый прямой вызов, а выход, смена пользователя и поздние ответы
не раскрывают данные завершённой сессии.
