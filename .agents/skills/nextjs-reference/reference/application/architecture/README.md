# Архитектурный профиль App Router

Перед изменением границ загрузи `unit-architecture`. Этот документ фиксирует решения проекта о физической форме,
средах выполнения и интеграции Next.js. Общие определения юнита, владельца и зависимости принадлежат профильному skill.

## Владельцы

| Слой | Ответственность |
| --- | --- |
| `app` | Файловые маршруты, адаптация URL и HTTP, подключение публичных провайдеров, метаданные и конфигурация сегментов |
| `compositions` | Завершённые экраны, каркасы и крупные блоки продукта; связь готовых возможностей с интерфейсом |
| `domains` | Предметные модели, правила доступа к предметным данным, операции, адаптеры, ожидаемые исходы и предметный UI |
| `infra` | Транспорт REST, технические интеграции, конфигурация окружения и диагностика |
| `ui` | Универсальные визуальные возможности и тема |
| `shared` | Чистые детерминированные функции, типы и константы без внешних ресурсов |

`app` является интеграционной границей, а не обязательным деревом юнитов. `page.tsx` и `route.ts` не нуждаются в
`index.ts`. Чтение cookie принадлежит серверной реализации сессии, а не `shared`. React-хук не является чистым
фундаментом только потому, что используется несколькими экранами.

В `compositions` используй группы `screens`, `layouts`, `widgets` и при реальной необходимости `route-boundaries`.
Группы не имеют фасетов. Граница маршрута нужна для повторяемого самостоятельного поведения, а не для дублирования
`loading.tsx`, `error.tsx` и других механизмов Next.js. Каркас принимает `children`, экран не импортирует дерево URL.

## Зависимости

Матрицу направлений и ограничения вложенности бери из `unit-architecture`. Допустимость слоя не разрешает обход
предметного владельца: экран не выполняет предметный HTTP-запрос через `infra`, а вызывает API домена.

- Межюнитные импорты, включая типы, динамические импорты и реэкспорты, проходят через публичный фасет.
- Внутри юнита используй относительные пути; снаружи — алиасы `compositions/*`, `domains/*`, `infra/*`, `ui/*`, `shared/*`.
- Нижние слои не импортируют `app`. Server Action, принадлежащая `app`, передаётся вниз как свойство, а не импортируется
  клиентской формой из `app/actions`.
- Вложенный юнит не импортирует родителя, предков или соседнего ребёнка. Зависимую часть оставь внутренней реализацией
  без фасета либо передай нужные данные через её контракт.
- Проверь весь граф юнитов на циклы; разделение одного владельца на серверные и клиентские файлы не устраняет цикл.

## Фасеты сред выполнения

| Файл | Публичный контракт | Ограничения |
| --- | --- | --- |
| `index.ts` | Универсальные типы, чистые функции, совместимые с RSC и клиентом компоненты | Нет зависимости от серверных ресурсов, хуков и браузерных API |
| `server.ts` | Серверные операции, чтение сессии, асинхронные серверные экраны | Содержит `import 'server-only'`; недоступен клиентскому графу |
| `client.ts` | Клиентские компоненты, Provider и хуки | Содержит `'use client'`; импорт и первоначальное отображение совместимы с SSR |
| `browser.ts` | Работа с DOM, хранилищем браузера или браузерным SDK | Содержит `import 'client-only'`; вызывается после монтирования или из события |

Создавай только нужные фасеты. Они состоят из директив, защитных импортов и явных реэкспортов, без реализации.
Названия зарезервированы для публичных границ; внутренний файл называй, например, `account.server.ts`, а не `server.ts`.
Исключение — файлы внутри полностью управляемого генератором `generated/` и `.svg-sprite/`.

Внутренние модули с секретами или серверным доступом также помечай `import 'server-only'`: защита одного фасета
не проверяет случайный относительный импорт между серверной и клиентской реализациями внутри юнита.

`'use client'` означает границу графа, а не запрет SSR. `client-only` запрещает серверное потребление в RSC, но не
отменяет серверное предварительное отображение клиентского дерева. В `browser`-реализации не обращайся к `window`
при импорте; несовместимый SDK загружай динамически из эффекта или события.

Серверный компонент может импортировать `client.ts`, чтобы **вывести** опубликованный компонент. Он не вызывает
клиентские хуки или функции из этого фасета. Клиентский компонент не импортирует `server.ts`, даже если использует
лишь одну «безопасную» функцию. Общий тип публикуй через универсальный фасет, а не через серверный.

```ts
// domains/account/server.ts
import 'server-only'
export { getAccount } from './operations/get-account.server'
export { updateAccount } from './operations/update-account.server'
```

```ts
// domains/account/client.ts
'use client'

export { useGetAccount } from './hooks/use-get-account/use-get-account.hook'
```

Не используй `'use server'` как маркер всего серверного слоя: эта директива объявляет удалённо вызываемые функции.
Правила публикации Server Actions находятся в [изменении данных](../data-fetching/mutations.md).

## Внутренняя структура

Основная реализация может оставаться в корне юнита. Сегменты добавляй вместе с кодом:

| Сегмент | Содержание |
| --- | --- |
| `types`, `config`, `helpers` | Типы, декларативные настройки и небольшие операции владельца |
| `operations` | Связные действия, серверные запросы и управление ресурсом |
| `adapters`, `mappers` | Преобразование внешнего API и DTO в предметный контракт домена |
| `errors`, `source-errors` | Предметные ошибки и распознавание ошибок источника внутри домена |
| `hooks`, `stores`, `providers` | Клиентские хуки, фабрики хранилищ и их область жизни |
| `ui`, `styles` | Внутренние компоненты и стили владельца |
| `generated` | Только результат генерации инфраструктурного клиента |

Сегмент не имеет своего фасета и не становится владельцем. Не создавай верхнеуровневые `server/` и `client/`, куда
собираются части разных доменов. Среда уточняет реализацию одного владельца, а не заменяет предметную архитектуру.

Домен принимает предметный вход, возвращает предметную модель и предусмотренные исходы. DTO, HTTP-ответ и ошибки
источника остаются в адаптере. Один mapper можно использовать в обеих средах, если его зависимости универсальны.
SWR и кеш Next.js не входят в транспорт. Путь `'/account'` не становится предметным правилом домена.

## Проверка

Для каждого изменённого публичного API выпиши потребителя, владельца и среду. Проверь транзитивные импорты, а затем
производственную сборку: одной проверки типов недостаточно для обнаружения смешения серверного и клиентского графов.
