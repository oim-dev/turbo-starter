# Кеширование и актуализация

Сначала проверь версию Next.js и `cacheComponents` в `next.config.*`. Профиль нового приложения использует
`cacheComponents: false` и явную политику каждого чтения. Настройки `create-next-app` могут отличаться; приведи их
к профилю при первоначальной настройке. Не переключай модель кеша существующего приложения в локальной задаче.

Этот выбор даёт предсказуемую исходную схему для REST-клиента: свежие данные запроса и отдельное включение общего
кеша для публичных результатов. Переход на Cache Components требует пересмотра потоковых границ и политики кеша;
его выполняют как связное изменение, а не как обязательное условие SSR.

## Разные области хранения

| Механизм | Что хранит | Область |
| --- | --- | --- |
| React `cache` | Результат одной серверной функции по аргументам | Серверное отображение React; не долговременный кеш между пользователями |
| Data Cache / `unstable_cache` | Результаты явно кешируемых чтений | Между запросами, согласно настройкам среды развёртывания |
| Full Route Cache | Предварительно построенные HTML и RSC | Статически построенный маршрут |
| Router Cache | Полученные и предварительно загруженные RSC-сегменты | Браузерная навигация Next.js |
| SWR | Клиентская проекция GET-данных | Экземпляр клиентского Provider |

Кеши не синхронизируются автоматически одной универсальной командой. `router.refresh()` запрашивает новое серверное
дерево, но не очищает Data Cache и SWR. `mutate` обновляет SWR, но не кеш Next.js. React `cache` не заменяет ни один
из них и не гарантирует дедупликацию произвольных вызовов вне серверного дерева React.

## Политика чтения без Cache Components

| Данные | Политика |
| --- | --- |
| Сессия, права, профиль, приватный список | `cache: 'no-store'` в серверном транспорте; без общего кеша |
| Публичные данные, требующие свежего ответа | Явный `no-store` |
| Публичный справочник или каталог с допустимой задержкой | Один явный кеш с временем жизни и тегами |
| Неизменяемая общая разметка | Допустимо предварительное построение маршрута |

Для стандартного `fetch` используй `cache` и `next.revalidate`/`next.tags` в соответствии с контрактом операции.
Не совмещай `no-store` и положительный `revalidate` одного запроса. В профиле с генерируемым REST-клиентом базовый
транспорт явно не кеширует запросы; публичный доменный результат при необходимости оборачивается в `unstable_cache`.
Так не приходится проталкивать неподдерживаемые поля `next` через типы генератора или создавать второй HTTP-клиент.

Пример файла `domains/catalog/operations/get-cached-catalog.server.ts` для публичного результата:

```ts
import 'server-only'
import { unstable_cache } from 'next/cache'
import { getCatalog } from '../adapters/get-catalog.server'

/** Возвращает публичный каталог с допустимой задержкой обновления в пять минут. */
export const getCachedCatalog = unstable_cache(getCatalog, ['catalog-v1'], {
  revalidate: 300,
  tags: ['catalog']
})
```

`getCatalog` в этом примере не читает cookie, не использует пользовательский клиент и принимает все параметры,
влияющие на результат, явно. Проверь, что locale, фильтр и иные варианты входят в аргументы кешируемой функции.
Тег нужен для актуализации, он не является ключом и не разделяет результаты пользователей.

Не оборачивай персональные данные в общий кеш, даже если ключ содержит `userId`: этот профиль не вводит хранение
персональных результатов между запросами. Не замыкай cookie, токен или настроенный под пользователя клиент в общей
кешируемой функции. Чтение сессии внутри React `cache` допустимо для дедупликации текущего серверного отображения.

Наличие Server Component само по себе не обещает выполнение при каждом запросе. Для данных, которым нужен запрос,
используй реальные Request APIs или явный `no-store`. Если запрос нужен по иной причине, например для настройки времени выполнения,
используй `await connection()` перед её чтением. Не ставь `force-dynamic` на корневой layout для всех маршрутов без причины.

## После успешной записи

Определи потребителей изменённых данных и обновляй только используемые ими области:

| Требуемый результат | Действие |
| --- | --- |
| Следующее чтение тега должно увидеть запись, без устаревшего ответа | `updateTag(tag)` внутри Server Action |
| Допустим устаревший ответ во время фонового обновления | `revalidateTag(tag, 'max')` в Action или Route Handler |
| Подписанный webhook требует немедленного истечения тега | `revalidateTag(tag, { expire: 0 })` после проверки источника |
| Обновить конкретное представление маршрута | `revalidatePath(path)`; для шаблона пути укажи тип `page` или `layout` |
| Получить новое некешируемое серверное дерево без перехода | `refresh()` внутри Action либо `router.refresh()` на клиенте |
| Обновить клиентский GET | `mutate` из текущего SWR Provider |

`updateTag` доступен только Server Actions. Не используй устаревший одноаргументный `revalidateTag`.
Актуализация из Route Handler помечает серверные данные, но не отправляет новое дерево в уже открытый браузер:
клиентскому сценарию может понадобиться обновление маршрута. `revalidatePath` не заменяет тег для того же ресурса на
других страницах. Не вызывай все функции подряд «для надёжности».

Имена тегов и перечень затрагиваемых ресурсов принадлежат домену. Путь и переход принадлежат интеграции маршрута.
Выполняй актуализацию после подтверждённой записи, до `redirect`. Повторный запрос — не повтор самой записи.

## Если Cache Components уже включены

Сохрани выбранную проектом модель и используй документацию его версии. Для Next.js 16:

1. Кешируемое публичное чтение обозначай `'use cache'`, задавай `cacheLife` и `cacheTag`.
2. Приватные чтения и `cookies()`/`headers()` оставляй вне общего кеша, под подходящей `Suspense`-границей.
3. Для параметров маршрута, известных только при запросе, также учитывай требуемую потоковую границу.
4. Не переносись механически с `dynamic`, `revalidate`, `fetchCache` и `unstable_cache`: ограничения этих API меняются
   при включении Cache Components. Не смешивай примеры двух моделей.
5. Настрой `partialPrefetching`, если это требует установленная версия; доступность и поведение проверяй по её документации.
6. Не включай экспериментальный приватный или удалённый кеш для обхода ошибки предварительного построения.

## Проверка

Проверяй кеш в производственном режиме, а не только через `next dev`. Проверь два последовательных чтения, изменение,
повторное чтение, другую страницу с тем же ресурсом и две разные сессии. При нескольких серверных экземплярах
проверь общий механизм хранения и доставки актуализации по [развёртыванию](../platform/README.md).
