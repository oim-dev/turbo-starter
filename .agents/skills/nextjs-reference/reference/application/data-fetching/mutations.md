# Изменение данных, Server Actions и Route Handlers

Сначала определи, нужна ли операции браузерная JWT-сессия. Наличие Server Actions не переносит её на Next.js-сервер.

| Потребитель и авторизация | Граница |
| --- | --- |
| Приватное действие интерфейса | Браузерная операция домена → браузерный REST-клиент → backend с Bearer JWT |
| Действие интерфейса без зависимости от браузерной сессии | Server Action, если требуется серверное выполнение |
| Публичный браузерный GET, webhook, публичное скачивание или внешний HTTP-потребитель | Route Handler, если нужен HTTP-контракт Next.js |
| Server Component | Прямое публичное чтение серверного API домена; без записи при отображении |

Не используй Server Actions как GET-загрузчики SWR: это удалённые вызовы через POST с собственной моделью выполнения.
Не дублируй уже существующий backend обработчиком Next.js только ради дополнительного уровня.

## Приватная браузерная операция

1. Дождись подтверждённой сессии по [авторизации](../authentication/README.md). Запрет кнопки или guard не заменяет
   независимую проверку прав backend.
2. Проверь ввод для удобства пользователя и вызови публичную операцию домена из клиентского события.
   Она использует `infra/<api>/browser`; DTO и ошибки источника остаются внутри доменного адаптера.
3. Backend повторно проверяет ввод, JWT, разрешение на действие и конкретный объект. Переданные `userId`, роль,
   цена или владелец записи не являются доказательством права.
4. Перед применением успеха или ошибки убедись, что поколение сессии не изменилось.
5. Обработай предусмотренный предметный результат. После успеха обнови нужные приватные GET в текущем SWR Provider
   и выполни действие интерфейса только для активного поколения.

JWT не передаётся в аргументах Server Action, `FormData`, Route Handler или URL. Приватная форма работает в браузере,
а не через нативную серверную отправку Next.js. Правила формы находятся в [формах](../forms/README.md).

Блокируй повторную отправку в интерфейсе. Для гарантии от повторной записи используй идемпотентность backend:
клиентская блокировка и отмена запроса её не обеспечивают. Не повторяй запись после неясного сетевого сбоя автоматически.

## Размещение Server Action

Action без зависимости от браузерной сессии находится в `app/<ветка>/actions.ts` с директивой `'use server'`.
В файле экспортируются только асинхронные действия. Типы результатов, схемы и константы принадлежат своим владельцам
и не экспортируются из него.

Action адаптирует внешний ввод, вызывает серверную операцию домена, актуализирует публичный кеш и при необходимости
выполняет переход. Она не реализует предметные правила, не создаёт HTTP-клиент и не получает браузерный JWT.
Защита такой серверной возможности определяется её реальным контрактом; отсутствие JWT не делает произвольную запись
разрешённой. Не используй служебные полномочия сервера для обхода пользовательского доступа backend.

Серверный `page.tsx` импортирует Action внутри `app` и передаёт её экрану или форме как `saveAction`.
Клиентские юниты не импортируют `app`; фасет `server.ts` также нельзя импортировать в клиентскую форму ради Action.

## Порядок выполнения Server Action

1. Прими вход как недоверенное значение. Проверь `FormData` или объект во время выполнения; TypeScript и `bind`
   не доказывают корректность или допустимость вызова.
2. Проверь ограничения операции по контракту backend. Если требуется текущая браузерная сессия, выбери браузерный
   процесс вместо продолжения этой Action.
3. Выполни запись через доменный адаптер и подготовь предусмотренный сериализуемый результат с признаком `status`.
4. После успеха актуализируй используемые публичные данные по [правилам кеша](caching.md).
5. Верни результат либо вызови `redirect` вне `try/catch`, перехватывающего ошибки записи.

Ожидаемые исходы определяются операцией: например `success`, `validation-error`, `conflict`.
Ошибка содержит безопасные коды и сообщения, а не `Error`, DTO, стек или технический ответ API.
Неожиданный сбой логируется на сервере и выбрасывается в канал ошибки Next.js по [качеству](../quality/README.md).

## Route Handler

Размещай обработчик в `app/api/<ресурс>/route.ts`. Экспортируй нужные методы `GET`, `POST` и другие именованными
функциями. В одном сегменте не совмещай `page.tsx` и `route.ts`.

Обработчик владеет HTTP-границей:

1. Разбирает URL, асинхронные `params`, заголовки и тело, проверяет вход и допустимость вызова.
2. Для webhook проверяет подпись и защиту от повторной обработки по контракту источника.
3. Вызывает серверный домен без браузерного JWT и переводит предусмотренный исход в статус и безопасный ответ.
4. Задаёт явный `Cache-Control` по публичности и актуальности ответа.
5. Обрабатывает неожиданный сбой в серверной диагностике и возвращает безопасный 5xx.

Не выполняй запись через GET. Не проксируй произвольный URL, все входные заголовки или cookie.
Route Handler не восстанавливает пользовательскую сессию из Bearer JWT: приватные запросы направляются браузером
в backend. Не добавляй установку серверной cookie для входа или обновления JWT.

## Проверка

Прямой защищённый вызов backend без JWT, с отклонённой сессией, неверным вводом или чужим идентификатором не получает
данные и не выполняет неразрешённую запись. Успех обновляет только активную область сессии; конфликт сохраняет ввод,
поздний результат не меняет новую сессию. Server Action и Route Handler не получают браузерный JWT,
а обычное отображение страницы не выполняет запись.
