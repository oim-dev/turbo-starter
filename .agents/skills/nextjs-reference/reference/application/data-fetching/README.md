# Получение данных

Первоначальные данные страницы загружай на сервере через публичный API предметного владельца:

```text
page.tsx → серверный экран → domains/<name>/server → доменный адаптер → infra/<api>/server → REST API
```

`page.tsx` также может вызвать домен, если данные нужны для решения о маршруте или метаданных. Не добавляй пустой
загрузчик-посредник только ради одинаковой цепочки. Server Component обращается к источнику напрямую через домен,
а не по HTTP к собственному `/api`: такой обход добавляет запрос и может не работать во время сборки.

## Порядок

1. Определи предметный результат, входные параметры и ожидаемые ошибки. Найди существующий домен и API-модуль.
2. Определи приватность, актуальность и нужные действия после записи по [кешированию](caching.md).
3. Создай или используй инфраструктурную операцию по [REST-клиенту](../../libraries/rest-api-codegen.md).
4. В доменном адаптере проверь внешний ответ и преобразуй DTO в предметную модель. Не выдавай DTO компоненту.
5. Опубликуй серверную операцию через `server.ts`. Зависимые от сессии операции сами проверяют доступ.
6. Выполни чтение в Server Component. Независимые запросы запускай параллельно; зависимые — последовательно.
7. Реши, достаточно ли серверного результата. Только при клиентской актуализации добавь хук SWR и начальные данные.
8. Проверь прямое открытие URL, отсутствие повторной первоначальной загрузки без причины и корректность пустого ответа.

## Выбор механизма

| Сценарий | Решение |
| --- | --- |
| Список, карточка, профиль при открытии URL | Серверная операция и Server Component |
| Независимый медленный блок | Серверный компонент под `Suspense` |
| Одно чтение для страницы и `generateMetadata` | Общая серверная операция, при необходимости React `cache` |
| Обновление по фокусу, опрос, интерактивная пагинация без перехода | Доменный SWR-хук с серверными исходными данными |
| Фильтр должен сохраняться в URL и работать при прямом открытии | Параметры URL → новая серверная загрузка |
| Императивный экспорт или скачивание | Публичная доменная операция; при необходимости отдельный HTTP-ответ |
| Запись | [Server Action или Route Handler](mutations.md) |
| Подписка | [Правила подписок](realtime-and-mocking.md) |

Не выполняй первоначальный GET через `useEffect` вместо SSR. Исключение — данные, которые по смыслу появляются
только после браузерного действия, например результат выбранного локального файла или геолокации.

## Клиентское обновление

Для same-origin чтения из браузера создай узкий Route Handler по публичному контракту интерфейса. Он проверяет
сессию и вызывает тот же серверный домен. Браузерный адаптер валидирует его ответ; SWR вызывает адаптер.
Не превращай Route Handler в открытый прокси с произвольным адресом источника.

Если приложение уже использует доступный браузеру внешний API с согласованной cookie-схемой и CORS, сохрани прямой
клиент. Не добавляй BFF только ради ещё одного уровня. Базовый выбор для нового приватного сценария — same-origin
обработчик: внутренняя авторизация внешнего сервиса остаётся на сервере Next.js.

SWR получает готовую предметную модель, ключ и правила актуализации по [инструкции библиотеки](../../libraries/swr.md).
У исходных серверных данных и дальнейших клиентских ответов должен быть один смысл. Не используй один ключ для
частичной карточки и полного профиля.

## Отсутствие данных и ошибки

Пустой список — успешный результат. Отсутствующая сущность — предусмотренный исход, который маршрут может
преобразовать в `notFound()`. Недоступный сервис не превращай в пустой список или 404.
Правила каналов ошибок, серверной диагностики и клиентских сообщений находятся в [качестве](../quality/README.md).
