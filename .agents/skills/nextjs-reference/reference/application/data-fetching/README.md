# Получение данных

Сначала определи, зависит ли результат от авторизации. Публичные первоначальные данные загружай на сервере через
API предметного владельца:

```text
page.tsx → серверный экран → domains/<name>/server → доменный адаптер → infra/<api>/server → REST API
```

Приватные данные загружает только браузер после подтверждения [JWT-сессии](../authentication/README.md):

```text
клиентский компонент → доменный SWR-хук или браузерная операция → доменный адаптер → infra/<api>/browser → backend
```

`page.tsx` также может вызвать публичный домен, если данные нужны для решения о маршруте или метаданных.
Не добавляй пустой загрузчик-посредник ради одинаковой цепочки. Server Component обращается к публичному источнику
через домен, а не по HTTP к собственному `/api`: такой обход добавляет запрос и может не работать во время сборки.

## Порядок

1. Определи предметный результат, входные параметры, зависимость от сессии и ожидаемые ошибки. Найди домен и API-модуль.
2. Выбери серверное публичное чтение или браузерное приватное. Определи актуальность и действия после записи по
   [кешированию](caching.md).
3. Используй инфраструктурную операцию по [REST-клиенту](../../libraries/rest-api-codegen.md).
4. В доменном адаптере проверь внешний ответ и преобразуй DTO в предметную модель. Не выдавай DTO компоненту.
5. Публичную серверную операцию опубликуй через `server.ts`, браузерную — через `browser.ts`, React-хук — через `client.ts`.
6. Независимые публичные серверные чтения запускай параллельно. Приватные чтения ожидают подтверждённую сессию;
   проверка сессии и вход имеют отдельный процесс по правилам авторизации.
7. Для публичного результата добавляй SWR только при необходимости клиентского обновления. Для приватного GET,
   участвующего в отображении, используй доменный SWR-хук без серверных начальных данных.
8. Проверь прямое открытие URL, начальную заглушку, момент начала запросов, пустой ответ и смену сессии.

## Выбор механизма

| Сценарий | Решение |
| --- | --- |
| Публичный список или карточка при открытии URL | Серверная операция и Server Component |
| Независимый медленный публичный блок | Серверный компонент под `Suspense` |
| Публичное чтение для страницы и `generateMetadata` | Общая серверная операция, при необходимости React `cache` |
| Обновляемые публичные данные | Доменный SWR-хук с публичными серверными исходными данными |
| Профиль, права или приватный список | Доменный SWR-хук после проверки сессии, до неё — `null` key |
| Публичный фильтр, сохраняемый в URL | Параметры URL → новая серверная загрузка |
| Приватный фильтр, сохраняемый в URL | Публичные параметры ресурса из URL → браузерное чтение после проверки сессии |
| Императивный экспорт или скачивание | Публичная операция домена в нужной среде; приватное скачивание — только в браузере |
| Запись | [Браузерная операция, Server Action или Route Handler](mutations.md) по потребителю и авторизации |
| Подписка | [Правила подписок](realtime-and-mocking.md) |

Не выполняй первоначальный публичный GET через `useEffect` вместо SSR. Приватное чтение после проверки сессии
не нарушает это правило: сервер не располагает его данными. Не запускай сеть во время отображения Client Component.

## Браузерные запросы

Приватный адаптер использует браузерный клиент backend с `Authorization: Bearer`. Не добавляй BFF, приватный
Route Handler или передачу JWT в Server Action ради повторения серверной цепочки. Защиту данных обеспечивает backend,
а не состояние guard. Удалённый backend должен разрешать браузерные запросы по своему контракту CORS.

Публичное браузерное чтение может использовать существующий доступный API или узкий Route Handler, если интерфейсу
нужен HTTP-контракт Next.js. Обработчик не становится открытым прокси с произвольным адресом источника.

SWR получает предметную модель, ключ и правила обновления по [инструкции библиотеки](../../libraries/swr.md).
Для публичного начального результата и последующих ответов сохраняй один контракт. Приватные результаты не передавай
с сервера через `fallback`, `fallbackData` или свойства; они появляются только в области подтверждённой браузерной сессии.

## Отсутствие данных и ошибки

Пустой список — успешный результат. Отсутствующая публичная сущность — предусмотренный исход, который маршрут может
преобразовать в `notFound()`. Отсутствие приватной сущности отображается в клиентской области после ответа backend.
Недоступный сервис не превращай в пустой список или 404. Каналы ошибок и безопасные сообщения описаны в
[качестве](../quality/README.md).
