# Структура и сборка приложения

Устройство юнитов определяется [архитектурным профилем](../architecture/README.md). Ниже показаны возможные части
приложения; пустые слои, группы и файлы не создавай.

```text
<приложение>/
├── .templates/
├── next.config.ts
├── next-env.d.ts
├── tsconfig.json
├── postcss.config.mjs
├── public/
└── src/
    ├── app/
    │   ├── layout.tsx
    │   ├── page.tsx
    │   ├── not-found.tsx
    │   ├── global-error.tsx
    │   ├── (account)/
    │   │   └── account/
    │   │       ├── page.tsx
    │   │       ├── loading.tsx
    │   │       ├── error.tsx
    │   │       └── actions.ts
    │   └── api/
    │       └── account/route.ts
    ├── compositions/
    │   ├── screens/
    │   ├── layouts/
    │   └── widgets/
    ├── domains/
    ├── infra/
    ├── ui/
    └── shared/
```

`next-env.d.ts` принадлежит Next.js и не редактируется вручную. Не добавляй `main.tsx`, `createRoot`, `hydrateRoot`,
React Router, `index.html` или SPA-перенаправление всех URL на один HTML-файл.

## Порядок создания

1. Настрой пакет приложения по [платформе](../platform/README.md): версии, команды Next.js, TypeScript и алиасы.
2. Настрой локальные шаблоны по [генератору](../../libraries/template-generation.md) до создания прикладных TSX.
3. Создай `ui/themes` с клиентским Provider темы по [Mantine](../../libraries/mantine.md).
4. Настрой [PostCSS](../../libraries/postcss.md). В корневом layout один раз подключи CSS библиотеки и публичный CSS темы.
5. Создай нужный серверный экран и каркас через CLI. Подключи их через фасеты в `page.tsx` и `layout.tsx`.
6. Добавь ближайшие состояния ожидания, ошибки и отсутствия данных по [страницам](../pages/README.md).
7. Проведи публичные данные от серверного доменного API до экрана. Для приватного сценария подключи браузерную
   проверку сессии, начальную заглушку и загрузку через клиентский доменный API.
8. Выполни проверки типов, линтера, сборки и прямого открытия URL по [качеству](../quality/README.md).

Файлы, созданные `create-next-app`, считаются результатом системного генератора. При ручной сборке приложения
связующие специальные файлы Next.js допускаются по [системным исключениям](../components/tsx-generation.md).

## Провайдеры

Корневой `layout.tsx` остаётся серверным и создаёт `<html lang="…">` и `<body>`. Внутри `body` он подключает
публичный клиентский `ThemeProvider` и передаёт готовое серверное содержимое через `children`.

Подключай Provider на ближайшем уровне, где действительно нужен его контракт. Реализация принадлежит владельцу:
тема — `ui/themes`, сессия — домену авторизации, область SWR — владельцу клиентского кеша.
`app/providers.tsx` допустим только как соединение уже готовых провайдеров, если такое соединение нужно.

Не собирай универсальный Provider со всеми зависимостями заранее. Клиентский Provider не превращает переданные
сервером `children` в клиентские модули и не даёт Server Components доступ к клиентскому Context.

При смене пользователя или организации явно переустанавливай область приватного состояния по
[правилам состояния](../state-management/README.md). Сохранение layout между переходами означает сохранение его Provider.
Provider авторизации начинает с `unknown`, восстанавливает JWT после монтирования и не получает серверную сессию
через свойства. Корневой layout и публичные данные остаются серверными.
