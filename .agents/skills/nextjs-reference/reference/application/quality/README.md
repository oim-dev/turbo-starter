# Ошибки и проверки

## Ожидаемый исход и дефект

Ожидаемые ошибки входят в предметный контракт: неверный ввод, конфликт, отсутствие сущности, истёкшая сессия или
запрет операции. Домен распознаёт технический ответ и возвращает предусмотренный результат. UI не разбирает DTO
ошибки сервиса и не принимает решение по случайной строке `message`.

Неизвестный ответ, нарушение контракта и ошибка программирования являются дефектами. Сохрани исходную причину
в серверной диагностике, а пользователю покажи безопасное сообщение. Не маскируй дефект пустым списком или 404.
Не логируй cookie, токены, полные тела запросов и персональные значения.

Если в проекте принят `ApplicationDefect`, используй его внутри соответствующей среды, нормализуя сбой один раз.
Не передавай экземпляр через границу RSC/Action. Серверный стек и `cause` остаются на сервере; для сопоставления
пользовательского сообщения и записи диагностики используй безопасный идентификатор, например `digest` Next.js.

| Источник | Канал обработки |
| --- | --- |
| Серверное отображение | Ожидаемый исход в UI/`notFound`/`redirect`; дефект в ближайшую `error.tsx` |
| Корневой layout | Независимая `global-error.tsx` со своим документом |
| Server Action | Ожидаемый сериализуемый результат; дефект логируется и выбрасывается |
| Route Handler | Согласованный HTTP-статус и безопасный ответ; дефект как 5xx |
| Клиентское событие | Явный `try/catch`, ожидаемый результат или безопасное сообщение и диагностика |
| SWR/подписка | Реальный тип канала ошибки, состояние данных и явный повтор |

`redirect()` и `notFound()` прерывают выполнение специальным исключением Next.js. Не оборачивай их общим
`catch`, преобразующим всё в предметную ошибку. Ограничь `try` вызовом источника, а решение маршрута выполни после него.
Если проекту нужен широкий перехват, используй документированный механизм повторного выбрасывания установленной
версии, а не распознавание внутреннего текста исключения.

`error.tsx` является Client Component и получает `error` и `reset`. Серверные детали ошибки в рабочем окружении могут быть
скрыты. Повтор через `reset` не исправляет неисправный источник и не очищает все кеши; при необходимости согласуй
его с обновлением серверного дерева. `global-error` не должен зависеть от Provider, который только что сломался.

## Проверки проекта

Запускай существующие команды. Для нового профиля минимальны:

```bash
npm run typecheck
npm run lint
npm run build
```

До них должна завершиться требуемая генерация REST/SVG. Установка из lock-файла и сборка выполняются в CI.
Проверки типов не заменяют производственную сборку: она проверяет RSC-границы, статическое построение и требования Suspense.

Тестируй значимые правила: доменные преобразования, проверку доступа, обработку ошибок, изоляцию сессии и
актуализацию после записи. Для чистых функций и клиентских компонентов подходит Vitest с принятым окружением.
Асинхронные Server Components и полный цикл App Router проверяй через запущенное приложение и Playwright;
не выдавай мок Next.js в jsdom за проверку SSR.

## Приёмка серверного сценария

Для затронутого сценария проверь:

1. Прямое открытие вложенного URL и его серверный HTML, включая данные после завершения потока.
2. Содержимое без JavaScript; отправку без JavaScript — только если это требование конкретной формы.
3. Гидратацию без предупреждений, затем переход через `Link`, перезагрузку и назад/вперёд.
4. Две независимые сессии, в том числе одновременное серверное чтение; отсутствие смешения данных и заголовков.
5. Прямой вызов изменяющей границы с неверным вводом, без сессии и с чужим ресурсом.
6. Запись и фактическое обновление всех используемых проекций: RSC, общий серверный кеш и SWR.
7. Выход, новую сессию, старый незавершённый запрос и сохранённые layout/Provider.
8. Ожидание, пустой результат, предусмотренную ошибку и неожиданный сбой.

Не запускай весь перечень для простой правки текста или локального CSS. Выбери проверки, подтверждающие изменённую
границу и поведение. При изменении кеша, сборщика, темы или маршрутизации проверяй собранное приложение через `next start`.

Сообщай только реально выполненные проверки. Если браузер или внешнее API недоступны, укажи конкретный непроверенный
сценарий; не подменяй его утверждением об успешной сборке.
