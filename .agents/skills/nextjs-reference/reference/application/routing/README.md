# Маршрутизация App Router

Дерево URL находится в `src/app`. Используй `page.tsx`, `layout.tsx`, `template.tsx`, группы маршрутов и динамические
сегменты Next.js. Не создавай второе дерево React Router, `Outlet`, `getServerSideProps`, `_app.tsx` или `_document.tsx`.

## Файловая граница

| Механизм | Назначение |
| --- | --- |
| `page.tsx` | Доступная по URL страница и адаптация входных параметров |
| `layout.tsx` | Сохраняемый каркас с `children` |
| `template.tsx` | Намеренное создание нового экземпляра поддерева при переходе |
| `loading.tsx` | Потоковое ожидание дочерней страницы/ветки |
| `error.tsx` | Клиентская граница ошибки дочернего сегмента |
| `not-found.tsx` | Интерфейс `notFound()` |
| `route.ts` | HTTP-обработчик, а не React-страница |
| `(group)` | Организация веток и каркасов без изменения URL |

Группа маршрутов не является архитектурной группой юнитов и не получает фасет. Имена файлов Next.js являются
обязательным внешним контрактом. Не переименовывай их ради общего правила `.screen.tsx`.

Layout сохраняется при переходах и не получает актуальные `searchParams` каждой страницы. Чтение query для
серверного результата выполняй в `page.tsx`; клиентское отображение текущего URL — в небольшой клиентской границе.
Не заменяй layout на template ради случайного исправления состояния: сначала определи нужный срок жизни.

## Переходы

- Для обычной внутренней ссылки используй `next/link`; для внешнего адреса и скачивания — семантическую ссылку.
- Для результата клиентского действия используй `useRouter` из `next/navigation`, а не `next/router`.
- На сервере используй `redirect` и `notFound` после получения предметного решения.
- Проверяй адрес из внешнего ввода перед передачей в переход; не передавай произвольный `returnTo` напрямую.
- Сохраняй в URL параметры, которые должны работать при прямом открытии, перезагрузке и возврате по истории.

Для чтения `useSearchParams` в предварительно строящемся маршруте выдели клиентскую часть под `Suspense`.
Не устраняй ошибку сборки превращением всей страницы в клиентскую. Если URL определяет первоначальные публичные данные,
предпочитай серверные `searchParams` страницы.
Для приватного запроса страница передаёт публичные параметры ресурса клиентской области, а она применяет их
после проверки JWT-сессии. Серверный `redirect` не определяет наличие браузерной сессии.

`router.refresh()` сохраняет подходящее клиентское состояние и не является полной перезагрузкой приложения.
Порядок обновления данных определяется [кешированием](../data-fetching/caching.md).

## Разделение кода и сложные маршруты

Next.js разделяет код по маршрутам. Не добавляй `lazy.ts` и `React.lazy` для каждой страницы по модели SPA.
`next/dynamic` нужен для отдельного тяжёлого интерактивного блока; ограничения SSR смотри в [отображении](../rendering/README.md).

Параллельные слоты и перехватывающие маршруты добавляй только для нужного сценария, например модального открытия
карточки поверх списка. Определи самостоятельный URL карточки и резервное содержимое `default.tsx` для слотов, включая неявный
`children`, где требуется восстановление. Проверь мягкий переход, прямое открытие и перезагрузку: результаты могут
намеренно различаться, но ни один не должен быть случайным 404.

`proxy.ts` находится рядом с `app` в `src/`, если он нужен. В Next.js 16 это механизм сетевой маршрутизации;
он не располагает браузерным JWT и не заменяет guard или проверку прав backend. В старом проекте сначала сверь
версию и среду существующего `middleware.ts`, а не переименовывай его механически.

## Проверка

Проверь вложенный URL напрямую, `Link`, назад/вперёд, обновление query, сохранение каркаса и состояние ошибок.
Убедись, что предварительная загрузка ссылки не запускает предметную запись.
