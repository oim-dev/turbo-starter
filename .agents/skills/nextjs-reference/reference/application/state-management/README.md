# Состояние в приложении с SSR

У каждого состояния определяй смысл, владельца, источник истины и срок жизни. Один смысл не должен одновременно
изменяться в свойствах компонента, SWR, Context и Zustand.

| Состояние | Механизм |
| --- | --- |
| Первоначальные серверные данные | Server Component и предметные свойства |
| Фильтр, сортировка или страница, которые должны переживать прямой переход | URL, проверяемый на сервере |
| Локальное открытие, выделение, временный ввод | `useState` или `useReducer` |
| Поля формы | `useForm` по [правилам форм](../forms/README.md) |
| GET-данные, обновляющиеся в браузере | Доменный SWR-хук |
| Разделяемое клиентское состояние с самостоятельным смыслом | Zustand в области Provider |
| Стабильная зависимость или экземпляр хранилища поддерева | Context |

Не добавляй Zustand, если локального состояния хватает. В существующем приложении сохраняй принятый менеджер
состояния вместо параллельного внедрения нового.

## Zustand и изоляция

Не создавай пользовательское хранилище через `create()` или `createStore()` на уровне общего модуля: процесс сервера
обслуживает разные запросы. Фабрика хранилища находится у предметного, визуального или технического владельца.

1. Экспортируй фабрику внутреннему Provider, а наружу — сам Provider и точные selector-хуки через `client.ts`.
2. Создавай экземпляр один раз на экземпляр Provider через ленивую инициализацию React state либо ref.
3. Передай одинаковый сериализуемый снимок для SSR и первого клиентского отображения.
4. Изменяй состояние только действиями владельца; компоненты подписываются на необходимые части.
5. Завершай связанные ресурсы при размонтировании. Не запускай сеть или подписку при создании хранилища.

Server Components не читают и не записывают клиентское хранилище. Они передают начальные значения через свойства.
Provider не обязан заново принимать новые `initialState` при каждом серверном обновлении: явно выбери сохранение
черновика, действие синхронизации либо перемонтирование по ключу сущности.

Для смены пользователя, организации или версии доступа используй новую область приватного состояния. Идентификатор
области не является токеном доступа. Перемонтирование по ключу сбрасывает хранилище и изолирует старые незавершённые запросы.
Не применяй `keepPreviousData` между разными пользовательскими областями.

## Сохранение в браузере

`localStorage` доступен только после монтирования. При `persist` отключи автоматическое восстановление до гидратации
поддерживаемым API установленной версии Zustand, затем выполни его явно в клиентском эффекте.

Определи формат, версию, миграцию, поведение при повреждённых данных и очистку при выходе. До восстановления сервер
и браузер показывают один начальный результат. Не сохраняй секреты, данные сессии и копию канонического серверного
кеша только ради переживания перезагрузки.

## Черновик и серверные данные

Черновик является отдельным состоянием: он может отличаться от подтверждённого серверного значения. Определи момент
создания, сохранение, конфликт и сброс. Фоновое чтение SWR или `router.refresh()` не должно стирать введённый текст.
Загруженный список, статус запроса и последнее значение подписки не зеркалируй в Zustand.

## Проверка

Проверь одинаковый первый HTML, два одновременных запроса с разными начальными данными, переход между сущностями,
выход и вход другим пользователем. Убедись, что возврат по истории и поздний ответ старого запроса не показывают
предыдущую приватную область.
