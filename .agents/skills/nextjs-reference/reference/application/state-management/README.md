# Состояние в приложении с SSR

У каждого состояния определяй смысл, владельца, источник истины и срок жизни. Один смысл не должен одновременно
изменяться в свойствах компонента, SWR, Context и Zustand.

| Состояние | Механизм |
| --- | --- |
| Первоначальные публичные данные | Server Component и предметные свойства |
| Приватные данные | Доменный SWR-хук после подтверждения браузерной сессии |
| Статус сессии | Домен авторизации; на сервере и при первом клиентском отображении — `unknown` |
| Фильтр, сортировка или страница, которые должны переживать прямой переход | URL, проверяемый на сервере |
| Локальное открытие, выделение, временный ввод | `useState` или `useReducer` |
| Поля формы | `useForm` по [правилам форм](../forms/README.md) |
| GET-данные, обновляющиеся в браузере | Доменный SWR-хук |
| Разделяемое клиентское состояние с самостоятельным смыслом | Zustand в области Provider |
| Стабильная зависимость или экземпляр хранилища поддерева | Context |

Не добавляй Zustand, если локального состояния хватает. В существующем приложении сохраняй принятый менеджер
состояния вместо параллельного внедрения нового.

## Zustand и изоляция

Не создавай пользовательское хранилище через `create()` или `createStore()` на уровне общего модуля: процесс сервера
обслуживает разные запросы. Фабрика хранилища находится у предметного, визуального или технического владельца.

1. Экспортируй фабрику внутреннему Provider, а наружу — сам Provider и точные selector-хуки через `client.ts`.
2. Создавай экземпляр один раз на экземпляр Provider через ленивую инициализацию React state либо ref.
3. Для публичного состояния передай одинаковый сериализуемый снимок для SSR и первого клиентского отображения.
   Приватное состояние начинает с нейтральных пустых значений; сессию восстанавливай после монтирования.
4. Изменяй состояние только действиями владельца; компоненты подписываются на необходимые части.
5. Завершай связанные ресурсы при размонтировании. Не запускай сеть или подписку при создании хранилища.

Server Components не читают и не записывают клиентское хранилище. Они передают публичные начальные значения через свойства.
Provider не обязан заново принимать новые `initialState` при каждом серверном обновлении: явно выбери сохранение
черновика, действие синхронизации либо перемонтирование по ключу сущности.

## Приватная область сессии

После подтверждения сессии создай отдельную область SWR и приватного Zustand. Используй безопасный `scopeId`, который
отличает поколения сессии, а при необходимости — организацию и версию доступа. Это не JWT и не его производное значение.
Повторный вход того же пользователя создаёт новую область; обновление JWT в прежней сессии само по себе её не меняет.

При завершении области сначала закрой приватный интерфейс и отключи запросы, затем очисти кеш, хранилища и черновики.
Перемонтирование Provider по ключу создаёт новые экземпляры, недоступные старым запросам. Отмени связанные запросы
и подписки, где это возможно. Сохраняемый layout не должен удерживать завершённую приватную область.

Одного перемонтирования или `abort` недостаточно для кода, который записывает во внешнее хранилище или вызывает обработчик.
Перед применением успешного ответа, ошибки, результата записи или проверки сессии сравни захваченное поколение с текущим.
Поздний результат не меняет состояние новой сессии. Не применяй `keepPreviousData` между областями и не восстанавливай
приватный кеш из браузерного хранения. Порядок входа и выхода определяет [авторизация](../authentication/README.md).

## Сохранение в браузере

`localStorage` доступен только после монтирования. При `persist` отключи автоматическое восстановление до гидратации
поддерживаемым API установленной версии Zustand, затем выполни его явно в клиентском эффекте.

Определи формат, версию, миграцию, поведение при повреждённых данных и очистку при выходе. До восстановления сервер
и браузер показывают один начальный результат. Не сохраняй JWT в общем состоянии или через `persist`.
Не сохраняй приватные ответы и копию канонического серверного кеша только ради перезагрузки.
Хранение JWT относится к отдельному контракту авторизации.

## Черновик и серверные данные

Черновик является отдельным состоянием: он может отличаться от подтверждённого серверного значения. Определи момент
создания, сохранение, конфликт и сброс. Фоновое чтение SWR или `router.refresh()` не должно стирать введённый текст.
Загруженный список, статус запроса и последнее значение подписки не зеркалируй в Zustand.

## Проверка

На сервере и при первом клиентском отображении приватная область пуста и показывает одну заглушку. До подтверждения
сессии приватных запросов нет. Выход, вход другим или тем же пользователем, переход между сущностями и возврат по истории
не восстанавливают старые данные. Поздний успех или `401` завершённой сессии не изменяет новую область.
