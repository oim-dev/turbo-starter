# Правила TypeScript

Этот skill определяет каноны написания TypeScript. Применяй его к клиентскому и серверному коду, библиотекам и
инструментам. Архитектуру, размещение ответственности и способ создания файлов определяет использующий проект.

## Порядок работы

1. Прочитай инструкции проекта, соседний код и настройки форматирования, линтера и TypeScript.
2. Определи режим применения по правилам ниже.
3. Примени описанные здесь правила оформления, именования, типизации и документирования к новому и затронутому коду.
4. Для повторяемых проверок внешних значений используй существующее общее решение. Если его нет, подключи
   [value-predicates](assets/value-predicates/README.md) к подходящему владельцу в проекте.
5. Проверь результат по списку в конце и запусти применимые проверки проекта.

## Режим применения

По умолчанию сохраняй стиль существующего проекта. Приоритет имеют обязательные инструкции и автоматические проверки,
затем соглашения затронутого файла и соседнего кода, затем правила этого skill для неурегулированных решений.
Не создавай новый локальный стиль и не переписывай незатронутый код ради единообразия.

Строго применяй каноны, если пользователь прямо этого требует или проект явно закрепляет этот skill. В этом режиме
правила skill определяют новый и затронутый код, а локальные соглашения дополняют их там, где правило отсутствует.
Не расширяй изменение на остальные файлы без отдельной задачи.

В обоих режимах обязательные проверки должны проходить. Если канон несовместим с настройками форматирования, линтера
или компилятора, не отключай проверки и не меняй конфигурацию без разрешения. Укажи конфликт и запроси решение,
если его нельзя разрешить в рамках задачи.

## Форматирование

- Не меняй конфигурацию инструментов в обычной задаче на правку кода.
- Форматируй только затронутый код. Не создавай изменения оформления по всему файлу или проекту.
- Не переименовывай публичные сущности и файлы без явной задачи.
- Используй 2 пробела и ориентир в 120 символов, если проект не задаёт иное.
- Переноси выражение ради читаемости, а не механического соблюдения лимита.
- Используй одинарные кавычки.
- Используй шаблонную строку для интерполяции или многострочного текста.
- Не ставь точки с запятой и завершающие запятые.
- Короткие объекты, массивы, кортежи и вызовы оставляй в одну строку.
- В многострочной форме размещай свойства, элементы, параметры и аргументы по одному на строке.

## Файлы и папки

- Папки и файлы называй в `kebab-case`.
- Имя должно описывать основную сущность или роль файла либо назначение папки.
- Не добавляй в имя технический термин, который не помогает отличить ответственность сущности.
- Не переименовывай существующую структуру только ради выравнивания соглашений.

### Ролевые файлы

Формат имени: `name.<role>.<ext>`. Суффикс в единственном числе описывает роль файла. Следуй локальному
варианту, если проект уже использует другое соглашение и не требует строгого применения канона.

Типовые суффиксы: `.hook`, `.store`, `.service`, `.type`, `.interface`, `.enum`, `.dto`, `.schema`, `.constant`,
`.config`, `.util`, `.lib`, `.test`, `.mock`.

Примеры: `user.type.ts`, `user.service.ts`, `user.test.ts`. Файл хука называй `use-name.hook.ts`.

## Вспомогательные функции

- Выноси логику в именованную функцию, когда имя делает основной сценарий понятнее, отделяет этап алгоритма,
  скрывает детали реализации, уменьшает вложенность или упрощает изолированную проверку.
- Единственное использование и небольшое количество строк не запрещают выделение функции.
- Не создавай функцию, которая только передаёт аргументы дальше и не добавляет понятного имени или границы реализации.

Размещение таких функций и правила общего использования определяет архитектура проекта.

## Импорты и экспорты

- Записывай все импорты одним непрерывным блоком без пустых строк между пакетами, алиасами, относительными путями и
  `import type`.
- Сохраняй порядок: внешние пакеты, алиасы проекта, относительные импорты. Внутри каждой части следуй порядку проекта.
- Для собственного кода предпочитай именованные экспорты.
- Экспорт по умолчанию используй только по требованию фреймворка, инструмента или устойчивого локального стандарта.
- Импорт пространства имён применяй только когда этого требует API библиотеки или локальный стандарт.
- Используй публичную точку входа модуля, не обходи её глубоким импортом.
- Не создавай файлы, собирающие реэкспорты, без публичной границы и реальных потребителей.
- Не создавай циклические зависимости ради удобного реэкспорта.
- Не меняй порядок и пути импортов только ради предпочтений в оформлении.

Конкретные алиасы, публичные точки входа и разрешённые направления зависимостей определяет проект.
Оформление единого блока импортов:

```ts
import { readFile } from 'node:fs/promises'
import { parseSettings } from './parse-settings'
import type { Settings } from './settings.type'
```

## Комментарии

- Объясняй назначение, ограничение, внешний контракт или неочевидную причину. Не пересказывай код.
- Ставь пробел после маркера комментария и точку в конце законченной фразы.
- Удаляй или обновляй комментарий вместе с изменением поведения.
- Не используй комментарий вместо понятного имени или декомпозиции.
- Логические части многострочного комментария разделяй одной пустой строкой.

Обязательность и содержание JSDoc определяет раздел [JSDoc](#jsdoc).

## Объявления и функции

- Используй `const` по умолчанию.
- Используй `let` только когда переменная действительно переназначается.
- Не используй `var`.
- Не изменяй входной объект или массив, если изменение не является явной частью контракта.
- Декомпозируй функцию, когда она одновременно решает несколько независимых задач.
- Не скрывай важный побочный эффект за именем, похожим на чистое вычисление.
- Не добавляй обобщённый параметр типа, если функция не связывает несколько типов и конкретный тип выражает контракт точнее.

```ts
/**
 * Возвращает отображаемое имя пользователя.
 */
const getDisplayName = (user: User): string => user.displayName
```

## Ранние возвраты и ветвление

- Используй ранние возвраты для отсутствующих данных, ошибок, запрещённых состояний и других исключающих условий.
- Сначала обрабатывай исключающие условия, затем размещай основной сценарий функции.
- Не добавляй `else` после ветки с безусловным `return` или `throw`.
- Не оборачивай основной сценарий в несколько уровней `if`, если вложенность можно заменить ранним возвратом.
- Исключай `null`, `undefined` и неподходящие варианты объединения типов проверкой с ранним возвратом.
- После проверки полагайся на сужение типа компилятором, а не обходи её через `as` или утверждение `!`.
- Не добавляй ранние возвраты механически, если линейное условие читается проще.

```ts
/**
 * Возвращает имя доступного активного пользователя.
 */
const getUserName = (user?: User): string => {
  if (!user) {
    return 'Гость'
  }

  if (!user.isActive) {
    return 'Неактивный пользователь'
  }

  return user.name
}
```

## Именование значений

- Переменные и функции называй в `camelCase`.
- Классы, типы и интерфейсы называй в `PascalCase`.
- Массивы называй во множественном числе.
- Списки идентификаторов называй `*Ids`.
- Словари и коллекции `Map` называй `*ById`, `*Map` или `*Dict`.
- Имена логических значений начинай с `is`, `has`, `can` или `should`.
- Внутренние обработчики называй `handle*`.
- Параметры и свойства для функций обратного вызова называй `on*`.
- Функция должна называться по выполняемому действию или возвращаемому значению.
- Проверку типа называй через `is*`, функцию утверждения через `assert*`.
- Избегай общих имён `data`, `item`, `value`, `result`, если роль можно выразить точнее.

```ts
const userIds: string[] = ['u1', 'u2']
const usersById: Record<string, User> = {}
const isReady = true

/**
 * Обрабатывает отправку формы.
 *
 * Запускает сохранение подготовленных данных.
 */
const handleSubmit = (): void => {
  // ...
}
```

## Типизация функций и API

- Типизируй параметры функций и компонентов.
- Для публичных функций указывай возвращаемый тип.
- Для локальной реализации используй вывод типа, когда тип очевиден и не является контрактом.
- Не дублируй выводимый тип локальной переменной явной аннотацией без причины.
- Не используй широкий тип, если контракт допускает точное объединение литералов или конкретную структуру.
- Не открывай внутренний тип через публичную сигнатуру случайно.
- Асинхронный публичный контракт выражай как `Promise<Result>` с конкретным типом результата.
- Функцию обратного вызова типизируй по её назначению, а не через общий `Function`.

```ts
/**
 * Загружает пользователя по идентификатору.
 */
export const getUser = async (userId: string): Promise<User> => {
  const response = await userApi.getUser(userId)

  return response.user
}
```

## `type` и `interface`

- Используй `type` для свойств компонентов, DTO, моделей отображения, объединений, отображаемых типов и композиции.
- Используй `interface` для расширяемых контрактов и слияния объявлений.
- Не смешивай `type` и `interface` для одной категории сущностей без причины.
- Не создавай отдельный псевдоним типа, если он не добавляет смысл и используется один раз в очевидной позиции.
- Не используй `enum`, если нужен обычный набор строковых или числовых значений во время выполнения.

```ts
/**
 * Свойства карточки пользователя.
 */
export type UserCardProps = {
  /** Отображаемый пользователь. */
  user: User

  /** Вызывается при выборе пользователя. */
  onSelect: (userId: string) => void
}

/**
 * Хранилище строковых значений.
 */
export interface StorageAdapter {
  /** Возвращает сохранённое значение. */
  get(key: string): Promise<string | null>

  /** Сохраняет значение по ключу. */
  set(key: string, value: string): Promise<void>
}
```

## Импорты и экспорты типов

- Импортируй сущность только для типов через `import type`.
- Экспортируй только тип через `export type`.
- Не заменяй импорт значения на `import type`, если сущность нужна во время выполнения.
- При включённом `verbatimModuleSyntax` не полагайся на удаление ошибочного импорта значения компилятором.

```ts
import { createUser } from './create-user'
import type { User } from './user.type'

export { UserCard } from './user-card'
export type { UserCardProps } from './types/user-card-props.type'
```

## `unknown`, `any` и утверждения типов

- Не используй `any` как обычный тип.
- Оставляй `any` только на неизбежной интеграционной границе с объяснимой причиной.
- Принимай внешние и недоверенные данные как `unknown`, затем сужай тип проверкой во время выполнения.
- Не используй `as` для обхода проверки типов.
- Утверждение типа допустимо после проверки значения или на границе с явно описанной причиной.
- Не используй утверждение `!`, если наличие значения можно доказать проверкой с ранним возвратом.
- Используй `as const` для литеральных конфигураций и объектов, заменяющих перечисления.
- Вместо `@ts-ignore` используй `@ts-expect-error` с объяснением причины, если подавление ошибки действительно необходимо.
- Удаляй подавление вместе с устранением несовместимости.

## Проверка значений во время выполнения

Типы TypeScript не проверяют данные во время выполнения. Проверяй ответы API, значения из хранилищ и URL,
пользовательский ввод, разобранный JSON и другие внешние значения до использования.

- Для повторяемой проверки создавай именованный предикат с возвращаемым типом `value is Type`.
- Базовые предикаты ограничивай проверками отсутствия значения, примитивов, строк, массивов, записей и объединений литералов.
- Предметные проверки, например `isOrder` или `isCity`, размещай рядом с владельцем данных.
- Для массива из внешнего `unknown` проверяй и сам массив, и каждый его элемент.
- Перед чтением полей объекта из `unknown` проверь, что это запись, затем наличие собственного свойства.
- Не смешивай отсутствие значения со значениями, приводимыми к `false`: `0`, `false` и `''` могут быть допустимыми.
- Прямой `.length` используй, когда нужен размер, индексный цикл или проверка длины строки.

```ts
/**
 * Проверяет значение на соответствие заказу.
 */
const isOrder = (value: unknown): value is Order => {
  return isRecord(value) && hasOwn(value, 'id') && isString(value.id)
}

if (isArrayOf(response.data, isOrder)) {
  // response.data: Order[]
}
```

Если проект не предоставляет эквивалентную базовую библиотеку, используй готовую реализацию из
[value-predicates](assets/value-predicates/README.md). Основной код импортирует её только через публичный API.

## Константы и литеральные типы

- Обычную локальную переменную, объявленную через `const`, называй в `camelCase`.
- Переиспользуемую константу верхнего уровня называй в `SCREAMING_SNAKE_CASE`.
- Связанный набор стабильных значений группируй в объект с `as const`.
- Ключи объекта, заменяющего перечисление, называй в `SCREAMING_SNAKE_CASE`.
- Значения сохраняют формат контракта и не обязаны повторять регистр ключей.
- Выводи объединение литералов из объекта, а не дублируй значения вручную.
- Не переименовывай непрозрачные значения внешнего API ради стиля кода.
- Коды ошибок, статусы, режимы, типы событий и флаги возможностей являются частными случаями этого подхода.

```ts
/**
 * Поддерживаемые состояния оплаты.
 */
export const PAYMENT_STATUS = {
  /** Оплата ожидает подтверждения. */
  PENDING: 'pending',

  /** Оплата подтверждена. */
  PAID: 'paid',

  /** Оплата завершилась ошибкой. */
  FAILED: 'failed'
} as const

/**
 * Состояние оплаты.
 */
export type PaymentStatus = (typeof PAYMENT_STATUS)[keyof typeof PAYMENT_STATUS]
```

## JSDoc

Каждая именованная TypeScript-функция, класс, `type`, `interface` и `enum` имеют многострочный JSDoc непосредственно
перед объявлением. Это относится и к внутренним объявлениям.
Правило распространяется на объявления функций, именованные функциональные выражения, стрелочные функции в именованной
переменной, обработчики и пользовательские хуки. Для членов внутри блоков действует отдельный формат ниже.

Внутри блоков типов, интерфейсов, классов и перечислений документируй члены однострочным JSDoc
`/** Назначение. */` на отдельной строке перед объявлением члена. Это относится к полям, методам, конструкторам,
аксессорам и значениям `enum`, включая вложенные поля. Не используй для них многострочный комментарий.
После `/**` и перед `*/` обязательно ставь пробел: `/** Возвращает сохранённое значение. */`.
Тот же однострочный формат применяй к полям объектов `as const`, заменяющих перечисления.

Константу документируй, если это публичный контракт, предметное ограничение, неочевидное значение или переиспользуемая
конфигурация.

Правило относится к исходному коду команды, включая заготовки, которые после создания редактируются разработчиком.
Не редактируй ради JSDoc файлы, полностью принадлежащие генератору: их оформление определяется инструментом,
а содержимое заменяется при повторном создании.

- Описывай назначение и ограничения сущности, а не синтаксис реализации.
- Не дублируй TypeScript-сигнатуру через `@param`, `@returns` и `@type`.
- Добавляй важную механику и результат только когда они неочевидны из имени и сигнатуры.
- Не документируй обычные локальные переменные и очевидные функции обратного вызова, записанные прямо в выражении.
- Не используй фиксированный шаблон и не раздувай простое описание обязательными секциями.

```ts
/**
 * Фильтры списка заказов.
 */
export type OrderFilters = {
  /** Идентификатор владельца заказов. */
  userId?: string

  /** Статус заказа для фильтрации. */
  status?: OrderStatus
}
```

## Проверка

- Режим применения определён по запросу пользователя и инструкциям проекта.
- В режиме стиля проекта сохранены существующие соглашения; в строгом режиме применены относящиеся к задаче каноны.
- Незатронутый код не переформатирован, публичные имена не изменены без задачи.
- Имена файлов и папок соответствуют их роли, ролевые суффиксы используются последовательно.
- Вспомогательные функции выделяют понятные операции и размещены по архитектуре проекта.
- Импорты записаны одним блоком, соблюдают публичные границы и не создают циклов.
- Комментарии добавляют контекст, которого нет в коде.
- Функции, значения, коллекции, обработчики и типы названы по роли.
- Для неизменяемых привязок используется `const`, а `let` применяется только при переназначении.
- Исключающие условия обеспечивают сужение типов без необоснованных `as` и `!`.
- Публичные контракты типизированы явно, локальные аннотации не дублируют вывод типов.
- `type` и `interface` используются последовательно по назначению.
- Импорты и экспорты типов оформлены явно.
- `any`, `unknown`, утверждения типов и подавления ошибок имеют конкретное обоснование.
- Внешние данные проверяются предикатами до использования, предметные проверки находятся у владельцев данных.
- Наборы значений объявлены один раз, а литеральные типы выведены из них.
- Именованные функции, классы и TypeScript-контракты имеют достаточный JSDoc.
- Перед объявлениями функций, классов, типов, интерфейсов и перечислений используется многострочный JSDoc.
- Члены внутри типов, интерфейсов, классов, перечислений и объектов, заменяющих перечисления, имеют однострочный JSDoc.
- Обязательные автоматические проверки пройдены.
