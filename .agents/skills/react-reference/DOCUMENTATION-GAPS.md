# Пробелы документации React Reference

Этот файл временно собирает нестыковки между документацией skill и рабочим `demo-app`, а также решения, для которых в
skill пока нет точной инструкции. Файл не является источником правил. Каждый пункт нужно проверить и перенести в основной
документ отдельной задачей, после чего удалить из этого списка.

## GAP-012: Проверка `generated`-кода на неиспользуемые параметры

**Состояние:** заблокирован версией генератора.

`@gromlab/rest-api-codegen@5.2.4` создаёт в `ApiRequestClient.request<T, E>` параметр типа `E`, который не используется в
сигнатуре. TypeScript 5.9 сообщает `TS6133` при включённом `noUnusedParameters`, хотя файл полностью принадлежит
генератору и не должен редактироваться вручную. В `demo-app` сохранены `strict` и `noUnusedLocals`, но
`noUnusedParameters` временно отключён для `tsconfig.app.json`.

Версия `5.2.4` остаётся последней опубликованной версией пакета. Нельзя исправлять созданный файл вручную или добавлять
его последующую правку в команду генерации.

Нужно использовать `E` в контракте создаваемого клиента либо предоставить способ исключить `generated`-код из этой
проверки. После выпуска исправления следует обновить закреплённую версию генератора, повторно создать клиент и вернуть
`noUnusedParameters` в `demo-app`.

## GAP-013: Поколения сессии и поздние ответы в демо

**Состояние:** правила уточнены, сквозной пример требует отдельного согласования.

Пользователь закрепил браузерный JWT как базовую авторизацию обоих референсов. Требуется не только разделять разных
пользователей, но и не принимать поздний результат завершённой сессии после нового входа, включая вход того же пользователя.
Прежние инструкции SWR допускали `userId` в общем кеше и не задавали полную границу между поколениями сессии.

В этой задаче основные правила перенесены в `reference/application/authentication/README.md`,
`reference/application/state-management/README.md` и `reference/libraries/swr/get-data.md`.
Они требуют отдельной приватной области на каждое поколение и проверки поколения перед изменением внешнего состояния.

В `demo-app` ключ проверки сессии постоянный, приватный ключ профиля использует только `userId`,
а `AuthenticationProvider` очищает записи через `mutate` без отдельного Provider на поколение.
Сравнение отклонённого токена защищает от части поздних `401`, но само по себе не показывает изоляцию
успешных ответов, параллельных входов и повторного входа того же пользователя.

Временно демо остаётся примером проверки JWT, guard и обработки отклонённого токена, а не доказательством
полного выполнения новых требований к изоляции. Отдельной задачей нужно согласовать
`demo-app/src/domains/authentication/` и `demo-app/src/domains/user/` с основными документами и проверить задержанные
успешные ответы, `401`, проверку сессии, вход и обновление токена между разными поколениями.
После подтверждения сценариев обновить раздел примера в основном документе авторизации и удалить этот пункт.
