# Браузерная JWT-сессия и доступ

Базовый способ авторизации React SPA — JWT в `Authorization: Bearer`. Браузер восстанавливает сессию, backend
подтверждает её действительность и проверяет права на каждую защищённую операцию и конкретные данные.
Наличие токена, его декодирование и клиентский guard не доказывают наличие доступа к API.

## Владельцы

- Домен авторизации владеет восстановлением, проверкой, входом, выходом и статусом сессии.
- Инфраструктурный API-модуль добавляет JWT перед защищённым запросом и хранит технические настройки транспорта.
- Предметный адаптер преобразует ответ и предусмотренные отказы backend в контракт своего домена.
- Guard отображает состояние проверки, ошибку, интерфейс гостя или подтверждённой сессии.
- Маршрутная граница связывает публичное решение домена с переходом по [маршрутизации](../routing/README.md).

Используй фасеты `index.ts` и при необходимости `lazy.ts` по [архитектурному профилю](../architecture/project-profile.md).
Не переноси в браузерную SPA серверные фасеты и правила SSR из `nextjs-reference`.

## Восстановление и вход

1. Начни со статуса `unknown`. Пока сессия не проверена, показывай нейтральное ожидание без защищённого содержимого.
2. Начни поколение попытки восстановления и прочитай JWT через принятый механизм браузерного хранения.
   Нет токена — состояние гостя; есть токен — выполни предусмотренную backend проверку сессии через доменный адаптер.
3. Применяй успешный ответ проверки или входа только к актуальной попытке установления сессии. После подтверждения
   создай её приватную область и установи `authenticated`.
4. Приватные GET, записи и подписки запускай только после этого подтверждения. Вход, проверка, обновление и завершение
   сессии имеют собственный контракт и не ожидают сами себя как обычные приватные запросы.
5. Отказ backend завершает отклонённую сессию. Временный сетевой сбой оставляет безопасное состояние ошибки с повтором,
   а не подтверждает сессию и не выдаётся за доказанный выход.

Новый вход также начинает новое поколение и завершает прежнюю приватную область. Если успешный ответ входа
подтверждает сессию по контракту backend, он может сразу открыть новую область; иначе выполни проверку сессии.

Место хранения, срок жизни, восстановление после перезагрузки и обновление JWT определяются контрактом приложения
и backend. Не добавляй способ сохранения или запрос обновления токена по предположению. Если проект использует `localStorage`,
технический владелец обрабатывает недоступное или повреждённое хранилище. Токен рассматривается как непрозрачная строка;
любой JavaScript страницы может получить к нему доступ, поэтому защита от XSS обязательна.

JWT добавляется настроенным транспортом перед каждым защищённым запросом, а не компонентом или SWR-хуком.
Не отправляй его в URL, ключах кеша, логах, телеметрии или стороннему сервису. Транспорт не импортирует домен
авторизации, SWR и роутер. Порядок настройки находится в [REST-клиенте](../../libraries/rest-api-codegen/transport.md).

## Приватные данные и интерфейс

Guard может не выводить дочерние компоненты, но не предотвращает прямой запрос к backend, заранее запущенный запрос
или загрузку кода роутером. Каждый приватный хук получает `null` key до подтверждения сессии, а запись и подписка
также проверяют активную область перед запуском. Backend независимо проверяет JWT и права; UI не скрывает
уже полученные без разрешения данные в расчёте на защиту guard.

Приватное состояние изолируется по сессии по [правилам состояния](../state-management/README.md#приватная-область-сессии),
а GET-кеш — по [SWR](../../libraries/swr/get-data.md#auth-scope). Публичный идентификатор области не является JWT
или его производным значением. Одного `userId` в общем кеше недостаточно для разделения последовательных входов
того же пользователя.

## Выход, смена сессии и поздние ответы

1. Синхронно закрой приватный интерфейс и отключи новые запросы и подписки.
2. Заверши поколение сессии, удали его JWT, очисти приватный кеш, состояние и черновики. Отмени старые запросы
   и подписки, где это возможно. Новую приватную область активируй только после проверки новой сессии.
3. Если backend поддерживает завершение сессии, уведомь его по принятому контракту. Ошибка уведомления не возвращает
   старый токен и UI; для запроса допустимо временно удержать прежний токен внутри операции выхода.
4. Не применяй результат запроса, проверки сессии, входа или обновления JWT, если их поколение уже завершено.
   Проверяй поколение и перед повтором запроса: старая операция не использует JWT нового пользователя.

Терминальный Bearer `401` после предусмотренной контрактом попытки обновления токена интерпретирует доменный адаптер
защищённой операции. Он вызывает публичное завершение сессии только если поколение и отклонённый токен
совпадают с текущими. Поздний `401` не завершает новую сессию, а поздний успешный ответ не восстанавливает старую.
`401` входа, регистрации и обновления токена имеет собственный смысл; временный сбой обновления не доказывает потерю сессии.
Не повторяй запись автоматически без гарантии идемпотентности backend.
