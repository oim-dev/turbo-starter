# Правила TSX

Этот skill определяет каноны написания React-компонентов на TypeScript. Размещение компонентов, архитектурные
границы, способ создания файлов и доступность API в выбранной среде определяет использующий проект.

## Порядок работы

1. Прочитай инструкции проекта и существующие компоненты. Установи назначение компонента, его владельца и среду
   выполнения. Используй только доступные в этой среде React API.
2. Загрузи skill `ts-styleguide`: он определяет режим применения, оформление TypeScript, типизацию и JSDoc.
3. Примени описанные ниже правила свойств, подготовки данных и JSX.
4. Для проверок значений используй существующие предикаты или подключи `value-predicates` по skill `ts-styleguide`.
5. Создавай и размещай файлы способом, принятым в проекте. При декомпозиции соблюдай тот же порядок.
6. Проверь компонент по списку в конце, затем запусти проверки типов, линтер и относящиеся к изменению проверки
   поведения и интерфейса.

## Зависимость от TypeScript

`ts-styleguide` обязателен для работы с этим skill. Устанавливай их вместе:

```bash
npx skills add gromlab-ru/js-reference --skill ts-styleguide tsx-styleguide
```

Если `ts-styleguide` недоступен, найди его по имени в публичном репозитории
[`gromlab-ru/js-reference`](https://github.com/gromlab-ru/js-reference) и начни с его точки входа.

Применяй выбранный режим TypeScript также к правилам TSX. Правила этого skill уточняют React-специфику:
например, JSDoc компонента имеет обязательный раздел применения, тогда как обычная функция следует общим правилам JSDoc.

## Подготовка JSX

JSX должен описывать готовое дерево, а не содержать вычисления, сложное ветвление и проверки формы данных.

## Свойства и формат элементов

Публичный тип свойств самостоятельного компонента объявляй в отдельном файле типов рядом с компонентом.
Конкретное размещение файла определяет структура проекта.

- Собственные параметры называй `{Name}Params`.
- Атрибуты корневого HTML-элемента называй `RootAttrs`.
- Итоговый публичный тип называй `{Name}Props`.
- Для компонента с DOM выводи `RootAttrs` из `ComponentPropsWithoutRef<'tag'>`.
- Через `Omit` исключай атрибуты, которыми компонент управляет сам или которые конфликтуют с собственными параметрами.
- Для компонента без собственного корневого DOM не создавай фиктивный `RootAttrs`.
- Не объявляй публичный контракт свойств внутри TSX-файла, если компонент является частью публичного API.

- Строковые свойства пиши в двойных кавычках, динамические значения передавай через `{...}`.
- Статическое логическое свойство записывай без `={true}`, динамическое — как `disabled={isSaving}`.
- Не добавляй пустые, дублирующиеся и неиспользуемые свойства.
- Короткий элемент оставляй в одну строку.
- В многострочном элементе размещай каждое свойство отдельно, закрывающую скобку — на отдельной строке.
- Открывающий и закрывающий теги элемента с вложенным деревом размещай на отдельных строках.

```tsx
<UserCard
  user={user}
  isSelected={isSelected}
  onSelect={handleSelect}
/>
```

## Предикаты и подготовка значений

- Проверяй данные предикатами до передачи в JSX.
- В JSX оставляй только простой предикат или заранее подготовленный логический флаг.
- Составные условия, подписи, длинные пути к данным и решения об отображении вычисляй до `return`.
- Логические флаги называй через `is*`, `has*`, `can*` или `should*`.
- Локальные данные называй с суффиксами `Data`, `Items` или `List`.
- Для проверки отсутствия используй `isDefined` или `isNotDefined`, если `0`, `false` и пустая строка допустимы.
- Не подменяй предикат неявным приведением к логическому значению, если тип или контракт значения шире `boolean`.
- Если базовых предикатов нет, подключи `value-predicates` по skill `ts-styleguide` до изменения JSX.

```tsx
const profileUser = currentUser.error ? null : currentUser.data
const ordersData = orders.data
const shouldShowEmptyState = !orders.isLoading && isEmptyArray(ordersData)

return (
  <>
    {isDefined(profileUser) && (
      <Profile user={profileUser} />
    )}

    {isNonEmptyArray(ordersData) && (
      <OrdersList orders={ordersData} />
    )}

    {shouldShowEmptyState && (
      <EmptyState />
    )}
  </>
)
```

## Формат условного отображения

После логического условия и `&& (` всегда переноси JSX на новую строку. Закрывающую `)` размещай на отдельной строке
перед `}`. Применяй этот формат даже к одному короткому элементу.

Плохо:

```tsx
{isNonEmptyArray(ordersData) && (<OrdersList orders={ordersData} />)}
```

Также не оставляй элемент без группирующих скобок:

```tsx
{isNonEmptyArray(ordersData) && <OrdersList orders={ordersData} />}
```

Хорошо:

```tsx
{isNonEmptyArray(ordersData) && (
  <OrdersList orders={ordersData} />
)}
```

## Проверка массивов

Не используй `.length` как логическое условие существования, пустоты или отображения массива.

Запрещённые формы:

```tsx
items?.length
items.length > 0
items.length !== 0
items.length === 0
!items.length
items && items.map(...)
items?.length && <ItemsList items={items} />
```

Такие проверки смешивают размер массива с решением об отображении, ухудшают сужение типов и могут вывести `0` в React.

- Для непустого типизированного массива используй `isNonEmptyArray`.
- Для пустого, отсутствующего или `undefined` списка используй `isEmptyArray` согласно контракту предиката.
- Для массива из внешнего `unknown` используй `isArrayOf(value, itemGuard)`.
- Сначала присвой длинный путь локальной переменной, затем проверь и используй её.
- Если массив заранее нормализован и список нужно отрисовать без отдельного условия, прямой `map` допустим.
- Не добавляй предикат вокруг `map`, если пустой массив и так должен вернуть пустое дерево.

```tsx
const ordersData = orders.data
const shouldShowEmptyState = isEmptyArray(ordersData) && !orders.isLoading

return (
  <>
    {isNonEmptyArray(ordersData) && (
      <OrdersList orders={ordersData} />
    )}

    {shouldShowEmptyState && (
      <EmptyState />
    )}
  </>
)
```

Нормализованный массив:

```tsx
const ordersData = orders.data ?? []

return ordersData.map((order) => (
  <OrderCard key={order.id} order={order} />
))
```

## Небольшие статические фрагменты

Записывай небольшой неизменяемый набор элементов прямо в JSX, если он используется один раз и каждый элемент имеет
собственное содержимое. Не создавай массив и `map` только ради единообразия разметки: искусственная модель данных скрывает
различия элементов и усложняет изменение текста или действий.

Используй массив и `map`, когда элементы действительно являются набором однородных данных, приходят извне, изменяются
вместе или обрабатываются общим правилом. Разные статические действия можно записать непосредственно:

```tsx
<nav>
  <a href="/account">
    Личный кабинет
  </a>
  <a href="/help">
    Помощь
  </a>
</nav>
```

## Тернарные выражения

Не используй тернарное выражение внутри JSX независимо от размера веток.

Плохо:

```tsx
return (
  <section>
    {isLoading ? <LoadingState /> : <OrdersList orders={orders} />}
  </section>
)
```

Для значения свойства вычисли результат до JSX:

```tsx
const submitLabel = isSaving ? 'Сохраняем' : 'Сохранить'

return <button type="submit">{submitLabel}</button>
```

Для необязательного небольшого элемента используй простой предикат:

```tsx
return isDefined(user) && (
  <UserCard user={user} />
)
```

Для взаимоисключающих состояний верхнего уровня используй ранний возврат после всех хуков:

```tsx
/**
 * Отображает список заказов пользователя.
 *
 * Используется для:
 *  - отображения состояний загрузки и ошибки заказов
 *  - отображения загруженного списка заказов
 */
const Orders = (props: OrdersProps) => {
  const orders = useOrders(props.userId)

  if (orders.isLoading) {
    return <LoadingState />
  }

  if (isDefined(orders.error)) {
    return <ErrorState error={orders.error} />
  }

  return <OrdersList orders={orders.data} />
}
```

- Не заменяй одно тернарное выражение парой дублирующих условий `condition && ...` и `!condition && ...`.
- Не используй немедленно вызываемую функцию, `switch` или функцию внутри JSX для обхода запрета тернарного выражения.
- Не размещай ранний возврат перед хуками, которые должны вызываться при каждом рендере.

## Хуки

Пользовательские хуки называй в форме `useSomething`. Их типизацию, имена файлов и JSDoc определяет `ts-styleguide`.
При разделении компонента сохраняй порядок вызова хуков и учитывай ограничения среды выполнения проекта.

## Декомпозиция JSX

Не сохраняй крупное JSX-дерево в переменную, если единственная цель переменной — позднее вставить это дерево
в собственный `return`.

Плохо:

```tsx
const ordersContent = (
  <section>
    <OrdersToolbar filters={filters} onChange={handleFilterChange} />
    <OrdersSummary orders={ordersData} />
    <OrdersGrid orders={ordersData} />
  </section>
)

return <main>{ordersContent}</main>
```

Вынеси крупную ветку в отдельный именованный компонент:

```tsx
return (
  <main>
    <OrdersSection
      filters={filters}
      orders={ordersData}
      onFilterChange={handleFilterChange}
    />
  </main>
)
```

Новый `OrdersSection` создай способом, принятым в проекте, рядом с кодом, которому он принадлежит.
Выделение компонента для читаемости само по себе не требует отдельной публичной архитектурной границы.

Выноси JSX в отдельный компонент, если выполняется хотя бы одно условие:

- ветка содержит несколько смысловых элементов;
- ветка имеет собственные условия, обработчики или подготовку данных;
- внутри ветки находится самостоятельный список или состояние интерфейса;
- разметка повторяется;
- JSX-переменная или функция построения JSX нужна только для уменьшения размера родительского `return`;
- блоку требуется комментарий, чтобы объяснить его назначение.

- Не заменяй компонент функцией `renderOrders()` или `getOrdersContent()`, возвращающей JSX.
- Не объявляй новый компонент внутри тела родительского компонента.
- Не выноси один простой элемент в компонент без самостоятельной ответственности.
- Передавай вложенному компоненту минимальные подготовленные данные и функции обратного вызова,
  а не весь результат запроса или хранилище без необходимости.

### Допустимое исключение для ReactNode

JSX-переменная допустима, когда React-элемент является значением для свойства, слота, конфигурации или внешнего API,
а не способом сократить собственный `return`.

```tsx
const emptyState = (
  <EmptyState
    description="Заказы не найдены"
    onReset={handleResetFilters}
  />
)

const tableConfig = {
  emptyState
}

return <OrdersTable config={tableConfig} orders={ordersData} />
```

- Используй исключение только когда API действительно принимает `ReactNode` или конфигурацию с React-элементом.
- Если свойство принимает `ReactNode` напрямую, короткий элемент передавай прямо в нём: `emptyState={<EmptyState />}`.
- Если крупную ветку можно представить отдельным компонентом, создай компонент и передай `<OrdersSection />`,
  а не храни его реализацию в переменной родителя.
- Не называй обычную переменную с деревом «слотом» или «конфигурацией» только для обхода правила декомпозиции.
- Не применяй это исключение к JSX-переменной, которая используется единственный раз внутри собственного `return`
  без требования API.

## Обёртки

- Не добавляй обёртку только ради форматирования или CSS.
- Учитывай влияние обёртки на DOM, расположение элементов и доступность.
- Используй Fragment, только когда нужен единый корень JSX без дополнительного DOM-узла.
- Не меняй HTML-семантику и ARIA в задаче только на оформление кода.

## Комментарии

### Верхнеуровневый комментарий компонента

Каждый React-компонент обязан иметь JSDoc непосредственно перед объявлением. Используй единую структуру: строка
назначения, пустая строка и раздел `Используется для:` с одной, двумя или тремя строками применения.

- Описывай назначение компонента и конкретные сценарии его применения.
- Не добавляй больше трёх строк применения; оставляй только сведения, необходимые для понимания контракта.
- Не пересказывай свойства, JSX-структуру и детали реализации.

```tsx
/**
 * Показывает текущую доступность пользователя.
 *
 * Используется для:
 *  - отображения состояния пользователя в списках и карточках
 */
export const UserStatus = (props: UserStatusProps) => {
  // ...
}
```

### Комментарии внутри JSX/TSX

Обязательный JSDoc компонента не является комментарием внутри JSX-дерева. Для самой разметки действуют отдельные правила:

- По умолчанию не комментируй JSX/TSX-дерево.
- Оставляй комментарии только для обходных решений, внешних ограничений и неочевидных причин.
- Используй только однострочную форму: `{/* Причина. */}`.
- Не комментируй очевидную структуру или назначение элемента.
- Если блоку нужен комментарий для объяснения назначения, выдели именованный компонент.

## Проверка

- Свойства оформлены единообразно, строки и выражения используют правильный синтаксис.
- Публичные типы свойств вынесены к компоненту и корректно выводят допустимые атрибуты корневого DOM-элемента.
- JSX использует предикаты и подготовленные логические флаги вместо неявного приведения типов.
- Условное отображение через `&&` переносит JSX между отдельными строками `&& (` и `)}`.
- Условия пустоты и непустоты массивов не используют `.length`.
- В JSX отсутствуют тернарные выражения, немедленно вызываемые функции, `switch` и функции для построения дерева.
- Крупные JSX-деревья не сохранены в переменные и вынесены в отдельные компоненты.
- JSX-переменные используются только как необходимые значения `ReactNode` для свойств, слотов, конфигурации или внешнего API.
- Ранний возврат расположен после обязательных хуков.
- Длинные пути к данным не дублируются.
- React-компонент имеет верхнеуровневый JSDoc с достаточным для понимания контракта контекстом.
- JSDoc компонента содержит назначение и раздел `Используется для:` с одной, двумя или тремя строками.
- Комментарии внутри TSX используются только для внешних ограничений, обходных решений и неочевидных причин.
- Нет случайных обёрток и неуместных комментариев.
