# Nest Backend

Базовый backend на NestJS 11, Prisma 7 и PostgreSQL 16. Два самостоятельных
HTTP-приложения обслуживают клиентские и административные аккаунты.

| Приложение | API                     | Swagger | Спецификация    |
| ---------- | ----------------------- | ------- | --------------- |
| Client API | `http://localhost:3001` | `/docs` | `/openapi.json` |
| Admin API  | `http://localhost:3002` | `/docs` | `/openapi.json` |

У каждого API собственные JWT secret, issuer/audience, refresh-cookie и таблицы
сессий. Клиентский токен не даёт доступа к Admin API и наоборот.

## Быстрый запуск

Нужны Node.js 24+, pnpm 11.25.0 и Docker Compose v2+. Команды выполняются из корня
монорепозитория:

```sh
pnpm install
pnpm infra:dev:up
pnpm backend:prisma:generate
pnpm backend:prisma:deploy
pnpm backend:prisma:seed
pnpm backend:dev
```

При стандартных настройках примеры `.env` копировать не обязательно. Для своих
значений используйте `infra/dev/env.example` и `apps/nest-backend/env.example`.
Явное окружение и `apps/nest-backend/.env` приоритетнее `infra/dev/.env`.
Перенесённый `DATABASE_URL` может указывать на другую БД: перед миграцией согласуйте
его с выбранным локальным окружением.

Seed идемпотентно создаёт администратора **`admin/admin`** для разработки.
Существующий пароль повторный запуск не меняет. Для production начальный пароль
задаётся через `BOOTSTRAP_ADMIN_PASSWORD`; development-пароль там не используется.

Отдельный запуск:

```sh
pnpm backend:dev:client
pnpm backend:dev:admin
```

## Аккаунт клиента

| Метод | Путь                 | Действие                                                    |
| ----- | -------------------- | ----------------------------------------------------------- |
| POST  | `/auth/register`     | Создать аккаунт: `login`, `password`, необязательное `name` |
| POST  | `/auth/login`        | Войти по `login` и `password`                               |
| POST  | `/auth/refresh`      | Обновить access-токен и ротировать refresh-cookie           |
| POST  | `/auth/logout`       | Отозвать сессию и очистить refresh-cookie                   |
| GET   | `/users/me`          | Получить собственный профиль                                |
| PATCH | `/users/me`          | Изменить `name`                                             |
| PUT   | `/users/me/login`    | Изменить `login`, подтвердив `currentPassword`              |
| PUT   | `/users/me/password` | Передать `currentPassword` и `newPassword`                  |

Профиль содержит `id`, `login`, `name`, `isActive`, `createdAt`, `updatedAt`.
Логин нормализуется в нижний регистр и уникален. После регистрации выполняется
отдельный вход. Пароль клиента — от 8 до 128 символов.

Смена логина или пароля отзывает все сессии пользователя, включая текущую, и
очищает refresh-cookie. Успешный ответ — `204`; затем необходим новый вход.
Обычное изменение имени сохраняет сессию.

## Аккаунт администратора

| Метод | Путь             | Действие                                          |
| ----- | ---------------- | ------------------------------------------------- |
| POST  | `/auth/login`    | Войти                                             |
| POST  | `/auth/refresh`  | Обновить токен                                    |
| POST  | `/auth/logout`   | Выйти                                             |
| GET   | `/auth/me`       | Получить собственный профиль                      |
| PUT   | `/auth/password` | Изменить пароль: `currentPassword`, `newPassword` |

Регистрация администратора через HTTP отсутствует. Первого администратора создаёт
seed; дополнительные аккаунты при необходимости создаются служебной CLI-командой.
После смены собственного пароля все административные сессии аккаунта отзываются.

## Браузерная авторизация

Access-токен приходит в JSON; для защищённых запросов передавайте
`Authorization: Bearer <accessToken>`. Refresh-токен хранится только в HttpOnly-cookie.
Браузерный клиент использует `credentials: 'include'`.

Для `/auth/login`, `/auth/refresh`, `/auth/logout` обязательны разрешённый `Origin`
и заголовок `X-CSRF-Protection: 1`. Разрешённые источники задаются отдельно:

- `CLIENT_ALLOWED_ORIGINS` — Next.js на порту 3005 и собственный Swagger на 3001;
- `ADMIN_ALLOWED_ORIGINS` — Vite на порту 5173 и собственный Swagger на 3002.

В dev по умолчанию разрешены эти порты для `localhost` и `127.0.0.1`.
При другом порте интерфейса обновите соответствующую переменную.
Refresh-токен одноразовый: повторное использование отзывает сессию. Не повторяйте
запрос refresh автоматически после потери ответа.

## Схема и миграции

В рабочей схеме остаются только клиентские/административные аккаунты, их сессии и
refresh-токены. Исторические миграции сохранены неизменными; новая очищающая миграция
удаляет сущности исходного продукта. Она предназначена для перевода копии проекта
к шаблону и удаляет прежние предметные данные.

Перед применением к существующей БД определите, нужны ли её данные. Для проверки
шаблона используйте отдельную БД. Автоматического сброса БД и volumes в командах нет.

## OpenAPI и SDK

Источники контрактов — DTO и контроллеры двух API. После их изменения:

```sh
pnpm rest-api-sdk:generate
pnpm rest-api-sdk:check-types
pnpm rest-api-sdk:build
```

Экспорт спецификаций не требует работающей БД. Операции SDK создаются закреплённой
версией `@gromlab/rest-api-codegen`; generated-код вручную не редактируется.
Пакеты `@demo/client-rest-api-sdk` и `@demo/admin-rest-api-sdk` пока сохраняют имена,
используемые перенесёнными frontend-приложениями. Их предметные контракты очищены.

## Проверки и сборка

```sh
pnpm backend:lint
pnpm backend:check-types
pnpm backend:build
```

Запуск собранных точек входа:

```sh
pnpm --filter @repo/nest-backend start:client
pnpm --filter @repo/nest-backend start:admin
```

Приёмка выполняется ручными HTTP-сценариями: регистрация, вход, refresh/logout,
профиль, смена логина/пароля и изоляция двух API.

## Следующий этап

Изображения, аватары, кроп и очереди будут реализованы отдельным этапом. Текущий
backend не зависит от S3. Локальный MinIO доступен как необязательный профиль
`storage` в [infra/dev](../../infra/dev/README.md).
