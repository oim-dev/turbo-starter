# Доступ административной панели

## Модель

Роли принадлежат только `AdminUser`. `ClientUser` и Client API независимы.
У аккаунта одна назначенная роль, у роли — набор permissions. Ключ роли стабилен.

| Роль | Права |
| --- | --- |
| OWNER | Все известные действия, включая системные |
| ADMIN | Все несистемные действия, включая будущие дополнения каталога |
| USER | Просмотр и изменение собственного имени, логина и пароля |
| Дополнительная | Выбранные OWNER несистемные действия; `account.read` обязателен |

Встроенные роли неизменяемы; дополнительные создаются, редактируются и удаляются
через интерфейс `/access`. Назначенную роль удалить нельзя. Исторический SUPPORT
сохраняется как дополнительная роль с `account.read` и `account.password.change`.

Каталог `PERMISSIONS` в `src/modules/admin-access/admin-permissions.ts` — источник
реальных действий. Создать строку permission без серверной реализации нельзя.
Новая возможность требует записи каталога и `@AdminPermissions(...)` на endpoint.
Закрытый endpoint без метаданных запрещён даже OWNER. Проверяются **все** объявленные
permissions. Guard читает текущую роль из БД, а не из JWT.

`system.access.manage` и `system.keycloak.manage` принадлежат только OWNER:
даже ошибочное наличие этих строк в дополнительной роли не даст системного доступа.
ADMIN не управляет ролями, назначениями, активацией аккаунтов или Keycloak.
Прикладных endpoint сверх собственного аккаунта пока нет, поэтому текущие
несистемные возможности ADMIN и USER совпадают; политика расширения у них различается.

## Начальная учётная запись

Admin API автоматически создаёт `admin/admin` с ролью OWNER при запуске только при пустой
таблице административных аккаунтов. Переименование владельца не восстанавливает
admin/admin при повторном запуске. Обязательной смены пароля нет. Пароль можно переопределить через
`BOOTSTRAP_ADMIN_PASSWORD`; повторный запуск не меняет существующий пароль или роль.
Владелец меняет пароль в интерфейсе `/profile` перед эксплуатацией production.
Новые аккаунты в интерфейсе по умолчанию получают USER, а не OWNER.

## Изменения и конкурентность

- Редактирование дополнительной роли принимает её `version`; устаревшая версия — 409.
- Изменение доступа аккаунта принимает `version`, соответствующую `authVersion`.
- Изменение роли отзывает сессии всех её пользователей, включая незавершённые OIDC-входы.
- Смена назначения, активности, собственного логина или пароля также отзывает сессии.
- Нельзя отключить или понизить последнего активного OWNER, включая конкурентные запросы.
- Нельзя активировать аккаунт без локального пароля и без активной identity.
- Системные изменения сериализованы PostgreSQL advisory lock, затем берутся user locks.
  После ожидания блокировок права и активная сессия инициатора проверяются заново.
- Аудит `AdminSecurityAudit` хранит actor/action/target/time, без паролей и секретов.

Изменение имени сессии не отзывает. Для смены логина нужен текущий локальный пароль,
если он есть; для SSO-only подтверждением служит активная собственная сессия.
У SSO-only аккаунта смена локального пароля запрещена.

## HTTP и интерфейс

`/auth/me` возвращает `role`, `roleName`, `permissions`, `name`, `hasLocalPassword`
и базовые поля аккаунта. UI использует permissions для навигации и форм, но сервер
проверяет доступ независимо. Права не сохраняются в токене или localStorage.

OWNER получает разделы «Управление доступом» и «Keycloak». Пользовательские формы
реализованы на `/profile`; смена логина/пароля завершает локальную сессию во вкладках.
Привязки issuer/sub, отключение локального пароля и отзыв всех сессий доступны OWNER
в блоке «Способы входа и сессии» выбранного аккаунта. Для SSO-only сначала создаётся
аккаунт с локальным паролем, затем привязывается Keycloak и отключается пароль.
Служебного CLI нет; первоначальная инициализация и очистка истёкших сессий автоматические.

## Обновление существующей установки

Сначала применить новую миграцию `20261009120000_admin_permissions_settings`, затем
выпустить новый Admin API и SPA/SDK. Client API контракт не изменён. Старый enum ролей
заменяется внешним ключом, пароли и существующие назначения OWNER/SUPPORT сохраняются.
Keycloak после миграции выключен; старые переменные ADMIN_KEYCLOAK_* не импортируются.
OWNER задаёт настройки и secret через UI; все значения хранятся в БД.
Миграция `20261009140000_keycloak_db_only` требует повторного ввода старого
зашифрованного secret и включения провайдера; внешнего ключа шифрования больше нет.

## Ручная приёмка

1. На отдельной БД: deploy, два запуска Admin API, login admin/admin; начальная роль OWNER.
2. Создать ADMIN и USER; их попытки читать/изменять `/access/*` и `/settings/keycloak` дают 403.
3. Дополнительная роль: создать с account.read, назначить аккаунту; смена пароля запрещена.
4. Добавить permission роли; прежний JWT пользователя отклоняется, после входа право доступно.
5. Неизвестные и системные permissions в дополнительной роли — 400; встроенные роли не меняются.
6. Устаревшие версии и удаление назначенной роли — 409; последнее OWNER-назначение защищено.
7. Изменить имя, логин и пароль в профиле; проверить отзыв прежних сессий и новый вход.
8. Keycloak: сохранить secret в БД, проверить hasSecret и отсутствие secret в ответе API.
9. Включить реальный провайдер через UI; пройти PKCE/callback/complete, затем изменить
   конфигурацию и проверить отзыв старой SSO-сессии и отказ незавершённого входа.
10. Проверить direct URL, reload, клавиатуру, мобильную навигацию и отсутствие секретов в storage.
