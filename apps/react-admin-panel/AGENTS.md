# Разработка React SPA

Разрабатывай приложение строго по [unit-architecture](../../.agents/skills/unit-architecture/SKILL.md)
и [react-reference](../../.agents/skills/react-reference/SKILL.md).
Для нового и изменяемого кода обязателен строгий режим React Reference
и применимых стайлгайдов: архитектурный профиль, прикладной процесс и каноны кода.
Каноны TypeScript, TSX, CSS и HTML определяют отдельные стайлгайды.

Локальные соглашения группировки `src/domains/` закреплены в
[README](README.md#доменные-группы) и дополняют архитектурный профиль React SPA.

## Профильные скиллы

Загружай скиллы до работы в соответствующей области. Их внутренние документы
выбирай по собственной точке входа скилла.

| Область | Обязательный скилл |
| --- | --- |
| TypeScript | [ts-styleguide](../../.agents/skills/ts-styleguide/SKILL.md) |
| React-компоненты и JSX в `.tsx` | [tsx-styleguide](../../.agents/skills/tsx-styleguide/SKILL.md) вместе с `ts-styleguide` |
| CSS и CSS Modules | [postcss-styleguide](../../.agents/skills/postcss-styleguide/SKILL.md) |
| Обычный HTML, включая `index.html` | [html-styleguide](../../.agents/skills/html-styleguide/SKILL.md); не применяется к JSX |
| Создание TSX и настройка `.templates` | [template-generation-ru](../../.agents/skills/template-generation-ru/SKILL.md) |
| REST-клиенты и SDK | [rest-api-codegen-ru](../../.agents/skills/rest-api-codegen-ru/SKILL.md) |
| Работа с `@gromlab/svg-sprites` | [svg-sprites-ru](../../.agents/skills/svg-sprites-ru/SKILL.md) |

Для генерации в этом проекте используй только `template-generation-ru`,
в том числе когда React Reference ссылается на англоязычный скилл генератора.
Новые TSX создавай по [инструкции React Reference](../../.agents/skills/react-reference/reference/application/components/tsx-generation.md)
через локальные шаблоны и `pnpm run create`; установленные скиллы вручную не меняй.

## Блокирующий протокол

Протокол обязателен для всех задач. Последующие разделы этого файла
дополняют его, но не отменяют и не ослабляют его требования.

1. **Прочитай основу.**
   Перед любой задачей полностью прочитай этот протокол, `SKILL.md`
   `unit-architecture` и `react-reference` и
   [архитектурный профиль React SPA](../../.agents/skills/react-reference/reference/application/architecture/project-profile.md).
   После каждого сжатия контекста всегда перечитывай протокол заново
   и восстанавливай необходимые инструкции. Пересказ не заменяет источник.

2. **Определи области работы и прочитай инструкции.**
   Разложи задачу на затронутые ответственности и прикладные области.
   Для каждой найди и прочитай соответствующие главы Unit Architecture,
   разделы React Reference и требуемые стайлгайды и профильные скиллы из таблицы выше.
   Читай конкретные инструкции до выбора решения. Одного SKILL.md недостаточно.

3. **Обоснуй решение до реализации.**
   Исследуй код и потребителей. Определи ответственность, ближайшего владельца,
   слой, необходимость отдельного юнита, публичный контракт и зависимости.
   Проверь фасеты, вложенность, колокацию и отсутствие циклов.
   Кратко зафиксируй: что и где меняется, по каким прочитанным инструкциям
   и как будет проверено.
   Для изменений интерфейса до реализации зафиксируй UI/UX-решение
   по разделу «Проектирование интерфейса». Без него реализация UI запрещена.

4. **Соблюдай блокировку.**
   До выполнения пунктов 1–3 запрещены правки, генерация кода
   и делегирование реализации. Разрешены исследование и уточнения.
   Если не определены владелец или применимые правила, источник недоступен
   либо обнаружено противоречие — останови затронутую работу и уточни решение.
   Не заменяй отсутствующее правило предположением или собственным исключением.

5. **Реализуй строго по выбранным правилам.**
   Следуй прочитанным инструкциям во время всей разработки.
   Существующий код и привычные подходы не оправдывают нарушение правил.
   Соблюдай предписанные способы генерации и использования библиотек.
   Перед работой в новой области повтори пункты 2–3 для этой области.
   Не расширяй изменения на незатронутый код ради единообразия.

6. **Проверь соответствие до завершения.**
   Сверь результат с checklist Unit Architecture, профилем React SPA
   и проверками всех использованных разделов React Reference и стайлгайдов.
   Выполни проверки проекта, а затронутые веб-сценарии проверь
   через `agent-browser` в собственной изолированной сессии.
   Для изменений интерфейса обязательна визуальная и сценарная проверка
   по разделу «Проверка через agent-browser».
   Исправь нарушения. Успешные lint, typecheck и build не заменяют
   архитектурную сверку и проверку соблюдения reference.
   При невыполненной обязательной проверке сообщи блокер,
   не объявляй приёмку завершённой.

## Ревью соблюдения референсов

Для приёмки нового и изменённого прикладного кода обязательна независимая сверка
с `react-reference`, архитектурным профилем и применимыми стайлгайдами.
Профильный агент — `react-reviewer`. Его задача — проверить не только поведение,
но и то, что исполнитель не обошёл предписанные подходы и инструменты скиллов.

- Применяй [общий протокол ревью](../../packages/dev-agents/playbooks/review.md)
  и [протокол соответствия референсам](../../packages/dev-agents/playbooks/reference-compliance.md).
- Исполнитель передаёт область изменения, применённые документы и разделы, решения
  о владельцах, UI/UX-решение при изменении интерфейса и фактические проверки.
  Для нового TSX нужны команда генерации, каталог запуска, результат и созданные пути
  либо конкретное основание системного исключения.
- Ревьювер самостоятельно читает нормы и сопоставляет их с кодом. Имя скилла в отчёте,
  сходство с шаблоном, соседний старый код и успешные lint/typecheck/build не доказывают соответствие.
- Результат содержит замечания с `path:line` и точным нормативным источником, а также
  таблицу «область → норма → код/доказательство → статус». Нарушения подхода нельзя
  пропускать только потому, что интерфейс работает или линтер их не обнаруживает.
- Неподтверждённый запуск генератора не объявляй доказанным ручным созданием;
  зафиксируй отсутствие подтверждения и запроси материал. Не выдавай положительную
  приёмку при нарушениях обязательных норм или непроверенных применимых требованиях.
- В режиме ревью не исправляй код: шаги «исправь нарушения» в протоколе разработки
  относятся к исполнителю. Ревьювер передаёт замечания основному агенту.

## Проектирование интерфейса

Визуальная целостность, адаптивность и удобство обязательны наравне
с функциональностью. Интерфейс «лишь бы работало» не является готовым результатом.

1. **Сначала спроектируй.**
   До написания UI определи задачу пользователя, главное действие,
   иерархию информации, композицию блоков и поведение на разных ширинах.
   Выбери типографику, отступы, плотность, цвета и визуальные акценты.
   Кратко зафиксируй решение в плане; детализация соответствует масштабу задачи.
   Опирайся на макет и дизайн-систему проекта. Если макета нет,
   самостоятельно сформируй цельное визуальное решение.

2. **Создавай продуманный визуал.**
   Обеспечь читаемую иерархию, согласованные размеры и отступы,
   аккуратные выравнивания, достаточный контраст и ясный главный акцент.
   Используй тему, токены и компоненты проекта по React Reference.
   Готовые компоненты требуют осмысленной композиции и настройки:
   их наличие само по себе не обеспечивает качественный дизайн.

3. **Проектируй полный пользовательский сценарий.**
   Сделай понятными следующий шаг, результат действия и способ исправить ошибку.
   Предусмотри применимые состояния: загрузку, пустой результат, ошибку,
   успех и недоступность действия. Сохраняй ввод при исправимых ошибках,
   предотвращай повторную отправку и сразу показывай обратную связь.
   Используй понятные подписи и сообщения на языке пользователя.

4. **Обеспечь адаптивность и доступность.**
   Продумай перестроение навигации, блоков, таблиц и действий на узком экране.
   Учитывай длинный текст и разный объём данных. Исключи случайные переполнения,
   перекрытия и скачки компоновки.
   Обеспечь семантику, доступные названия, управление клавиатурой,
   видимый фокус и удобные области нажатия.
   Анимации должны помогать взаимодействию и учитывать reduced motion.

## Проверка через agent-browser

Инструмент закреплён в devDependencies этого приложения и используется любым
кодовым агентом через CLI. Все команды ниже выполняются из `apps/react-admin-panel`.
Запускай `pnpm run browser <команда>`, чтобы использовать установленную проектную версию
и явный конфиг [agent-browser.json](agent-browser.json).
Перед первым запуском на машине выполни `pnpm run browser:install`.
Установка и примеры описаны в [README](README.md#браузерный-инструмент).

1. **Подготовь проверку.**
   Прочитай актуальную инструкцию `pnpm run browser skills get core` и проверь
   доступные команды через `pnpm run browser --help`.
   Для каждой задачи всегда создавай собственную изолированную сессию
   `agent-browser` с уникальным именем. Явно указывай её во всех командах,
   включая закрытие. Использовать сессию по умолчанию, общие или чужие
   сессии запрещено. Не переключай и не закрывай чужие вкладки и сессии.
   Дополнительная вкладка в общей сессии не считается изоляцией.
   Используй headless-браузер проекта без пользовательского профиля, `--cdp`
   и `--auto-connect`; `--headed` допустим по явному запросу пользователя.
   Не полагайся на сохранение shell-переменных между вызовами инструментов:
   повторяй выбранное имя через `--session <имя>` в каждом вызове.
   Открой работающее приложение и воспроизведи затронутый сценарий.

2. **Проверь поведение.**
   Пройди сценарий от входа до результата: навигацию, ввод, отправку,
   применимые ошибки и восстановление после них.
   Проверь клавиатуру и фокус, ошибки браузерной консоли и запросов.
   Проверяй наблюдаемый результат действия, а не только успешность клика.
   После переходов и изменения страницы обновляй `snapshot -i`; ожидай
   конкретный текст, элемент или URL. Смену аккаунтов проверяй в одной сессии,
   синхронизацию авторизации — в нескольких вкладках этой же сессии.
   Конфиг отключает автоматическое принятие `alert` и `beforeunload`:
   проверяй диалоги через `dialog status` и явно выбирай `dialog accept`
   или `dialog dismiss` по проверяемому сценарию.

3. **Проверь внешний вид и доработай.**
   Сделай и просмотри скриншоты на узкой, промежуточной и широкой ширине.
   Сравни результат с макетом или зафиксированным UI/UX-решением:
   композицию, типографику, отступы, акценты и состояния.
   DOM-снимок не заменяет просмотр изображения.
   Исправляй обнаруженные недостатки и повторяй затронутые проверки
   до выполнения критериев качества.

4. **Подтверди результат.**
   Кратко укажи проверенные сценарии, размеры viewport, результаты
   и пути к скриншотам. Сохраняй артефакты в корневом
   `.artifacts/react-admin-panel/<имя-сессии>/`, отдельно от исходников приложения.
   Закрой собственную браузерную сессию через
   `pnpm run browser --session <имя> close`.
   Если обязательная проверка недоступна, сообщи конкретный блокер;
   не объявляй интерфейс полностью проверенным.
