# Авторизация администратора

Домен `auth` владеет входом, восстановлением и завершением административной сессии,
решением о доступе к панели, текущим администратором и формой входа.
Технический источник — публичный фасет `infra/backend-admin-api`.

## Публичный контракт

```tsx
import { AuthProvider, SignInForm, useAuthentication, useGetCurrentUser } from 'domains/auth'
```

- `AuthProvider` подключается один раз в `app/App.tsx`, запускает восстановление,
  планирует refresh и создаёт SWR-кеш текущей сессии.
- `SignInForm` содержит поля Mantine, валидацию, отправку и сообщения об ошибках.
  Форма не зависит от роутера. Экран определяет её размещение.
- `useAuthentication()` возвращает `checking`, `authenticated`, `guest` или `error`
  и безопасную доменную причину отказа.
- `useGetCurrentUser()` возвращает стандартный `SWRResponse` с моделью
  `{ id, login, isActive, role, createdAt, updatedAt }` без технической версии доступа.
  Профиль хранится в SWR, а не копируется в Zustand.
- `getCurrentUser()` предоставляет тот же GET для императивной проверки.
- `signIn({ login, password })`, `logout()` и `retryBootstrap()` выполняют сценарии
  вне жизненного цикла SWR. Ошибки различаются через `isAuthError()` и `AUTH_ERROR_CODE`.

Внешние потребители импортируют только `domains/auth`. Внутренние `ui/`, `providers/`,
адаптеры и store не образуют отдельных юнитов и не имеют собственных фасетов.

## Жизненный цикл

1. При запуске домен читает маркер общей cookie под Web Lock. Разрешённое
   восстановление выполняет один `adminBrowserRefresh()`.
2. После входа или refresh ответ проверяется во время выполнения. Access token
   передаётся в память API-клиента; токен не разбирается как JWT и не сохраняется
   в storage, Zustand или ключах SWR.
3. `adminAuthMe()` подтверждает активного администратора до открытия приватного UI.
4. Домен планирует refresh по `expiresIn` с запасом, учитывая абсолютный
   `sessionExpiresAt`. Обычные HTTP-запросы автоматически не повторяются.
5. Выход синхронно удаляет credential и закрывает приватный UI, затем отзывает
   серверную сессию. Неподтверждённый сервером выход имеет код `LOGOUT_INCOMPLETE`.
6. Завершение или смена сессии меняет поколение SWR-провайдера. Ответ старого
   запроса не может попасть в кеш следующего входа.

Отклонённый Bearer сравнивается с актуальным credential перед завершением сессии.
Поздние результаты входа и восстановления проверяют ревизию пользовательского
намерения и не заменяют более новый вход или выход.

## Несколько вкладок

`infra/browser-storage` предоставляет Web Locks, BroadcastChannel и доступ к storage.
Домен хранит под ключом `admin-auth-session-v1` только случайное поколение входа,
фазу `ready` / `exchanging` / `signed-out` и безопасный код причины завершения.

Все изменяющие cookie операции выполняются под одной origin-scoped блокировкой.
Маркер `exchanging` записывается **до** HTTP-запроса. Если вкладка закрылась или
результат refresh неизвестен, следующий запуск требует явного входа вместо
повторного использования одноразового refresh token. Ответы `429` и отказ проверки
запроса допускают явное повторное восстановление.

Для нескольких вкладок нужны один browser origin, безопасный контекст (HTTPS или локальный localhost), Web Locks,
BroadcastChannel и доступный localStorage. Уведомления не передают данные сессии:
получатель перечитывает маркер под блокировкой.

## Генерация и проверки

Существующие `AuthProvider` и `SignInForm` редактируются без повторной генерации.
Новые TSX создаются по [локальным шаблонам](../../../.templates/README.md) из корня приложения;
внутренние компоненты домена используют `ui-component` без собственного фасета.

Проверки из корня репозитория:

```sh
export PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false
pnpm --dir apps/react-admin-panel run lint
pnpm --dir apps/react-admin-panel run check-types
pnpm --dir apps/react-admin-panel run build
```
