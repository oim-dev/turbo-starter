## Граница SSR и авторизации

SSR сохраняется **только для данных, не зависящих от авторизации**. Не применяй SSR ко всем данным страницы автоматически.
Перед выбором среды проверь, зависит ли запрос, доступ к данным или содержимое ответа от текущего пользователя,
его сессии, роли или прав. Публичность URL сама по себе не делает данные независимыми от авторизации.

- Независимые от авторизации данные, например общедоступную справочную информацию, можно загружать и рендерить на сервере.
- Данные, зависящие от авторизации, относятся к клиентским данным: загружай и отображай их только в браузере
  после восстановления и проверки сессии. При SSR вместо них рендерится нейтральная заглушка без персональных значений.
- На смешанной странице сохраняй SSR публичной части, а для авторизационно-зависимых блоков выводи заглушки.
- Next.js не читает credentials и не загружает авторизационно-зависимые данные для SSR, metadata, RSC payload
  или начального кеша клиентских компонентов. Не передавай такие данные через props или `fallbackData` с сервера.
- `'use client'` не отключает серверный prerender: начальный серверный и клиентский рендеры должны совпадать
  и показывать заглушку. Приватная загрузка запускается только в браузерном lifecycle.
- Клиентский guard не защищает переданные ему Server Components: они могут выполниться до проверки guard.
  Не передавай под guard серверное поддерево, которое загружает или рендерит авторизационно-зависимые данные.
- Проверяй production HTML и RSC payload с действующей сессией: авторизационно-зависимые данные должны отсутствовать,
  а после гидратации и проверки сессии — появляться через клиентскую загрузку.

Основание: [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components).

## Обязательный порядок разработки

Для задач по `apps/next-web-app`, включая связанные изменения вне приложения,
РЕАЛИЗАЦИЯ ЗАПРЕЩЕНА до выполнения всех четырёх пунктов ниже.
До допуска разрешены только чтение, исследование, уточнения и планирование.
Запрет включает изменение файлов, генерацию кода и делегирование реализации.

Это Next.js-приложение с App Router, а `react-reference` рассчитан на React SPA.
Здесь он намеренно используется как источник совместимых правил, а не как готовая инструкция для Next.js.
Инструкции React Reference, противоречащие Next.js или нарушающие SSR, RSC либо гидратацию,
не применяй: используй соответствующий механизм Next.js и обоснуй исключение в плане.
Исключение касается только несовместимых инструкций React Reference.
**Инварианты Unit Architecture обязательны без послаблений: архитектура универсальна.**

1. **Прочитай skills.**
   Загрузи [unit-architecture](../../.agents/skills/unit-architecture/SKILL.md)
   и [react-reference](../../.claude/skills/react-reference/SKILL.md), полностью прочитай
   их `SKILL.md`. Используй актуальные документы, а не память прошлых задач.

2. **Определи архитектуру изменения.**
   Прочитай применимый архитектурный профиль и необходимые по задаче
   разделы Unit Architecture, включая материалы о Next.js и SSR, когда они затронуты.
   Исследуй код и потребителей. Определи ответственность, ближайшего владельца,
   слой, необходимость отдельного юнита, публичный контракт, зависимости и среды выполнения.
   Проверь фасеты, вложенность, отсутствие циклов и совместимость транзитивных импортов со средой.
   Выбирай владельца по ответственности, не по типу файла или библиотеке.
   Существующий код сам по себе не доказывает архитектурную корректность.
   Не переноси SPA-профиль или дерево примера в Next.js автоматически.

3. **Выбери инструкции реализации.**
   По карте `react-reference` найди и прочитай нужные прикладные разделы,
   затем необходимые инструкции библиотек, правила кода и профильные skills.
   Читай только относящуюся к задаче документацию, не весь reference.
   Framework-поведение проверяй по [официальной документации Next.js](https://nextjs.org/docs)
   для используемой версии. Сохраняй границы Server/Client Components;
   server-only код и секреты не должны попадать на клиент.
   Client Components также могут рендериться на сервере: `use client` не отменяет SSR.
   Не отключай SSR и не превращай приложение в SPA ради соблюдения React Reference.

4. **Зафиксируй план.**
   До первой правки составь краткий план: что изменить, у какого владельца,
   по каким прочитанным документам и как проверить результат.
   Для каждого исключения из React Reference укажи конкретное правило,
   подтверждённый конфликт и выбранный механизм со ссылкой на документацию Next.js.
   План должен соответствовать Unit Architecture и применимым инструкциям React Reference.

**Допуск получен только после фактического выполнения всех четырёх пунктов.**
Если необходимые источники недоступны или остаётся влияющая на решение
неопределённость, реализация заблокирована: уточни вопрос, не угадывай.

После допуска строго следуй плану, Unit Architecture и совместимым правилам React Reference.
Для нового и изменяемого кода обязателен строгий режим применимых правил кода reference.
Экраны сохраняют полный каркас генератора: `props`, отдельный файл типов, CSS Module и публичный фасет.
Даже без собственных параметров оставляй `ScreenParams`, `RootAttrs` и `ScreenProps`; не сокращай экран до функции без props.
Иные самовольные исключения и замена правил привычными подходами запрещены.
При появлении новой области задачи сначала дополни чтение и план.
Перед завершением проверь архитектуру, соблюдение применимых правил и выполни проверки проекта.
Для изменений рендеринга и границ server/client проверь production build, SSR и гидратацию затронутых маршрутов.

## Архитектурный профиль

Область действия — `apps/next-web-app/src`, Next.js 16 App Router. Поддерживаются RSC,
серверный prerender Client Components и выполнение в браузере. Инварианты Unit Architecture
обязательны во всех средах; исходный [профиль React Reference](../../.claude/skills/react-reference/reference/application/architecture/project-profile.md)
применяется с перечисленными здесь адаптациями Next.js.

### Слои и зависимости

| Путь от `src` | Ответственность | Алиас |
| --- | --- | --- |
| `app` | Framework-файлы, дерево URL, metadata и подключение готовых API | `app/*` |
| `compositions` | Вёрстка, каркасы и экранные сценарии | `compositions/*` |
| `domains` | Предметные контракты, правила, операции и адаптация данных | `domains/*` |
| `infra` | Технические интеграции и ресурсы | `infra/*` |
| `ui` | Универсальные визуальные возможности и тема | `ui/*` |
| `shared` | Чистые детерминированные функции, типы и значения | `shared/*` |

Алиасы определяются в `tsconfig.json`; Next.js читает их напрямую. Межюнитные импорты
используют алиас слоя и публичный фасет, внутренние импорты владельца — относительные.

Разрешённые зависимости:

- `app` → все слои;
- `compositions` → `compositions`, `domains`, `infra`, `ui`, `shared`;
- `domains` → `domains`, `infra`, `ui`, `shared`;
- `infra` → `infra`, `ui`, `shared`;
- `ui` → `ui`, `shared`;
- `shared` → `shared`.

Граф ацикличен, включая динамические импорты, реэкспорты и `import type`.
Фасет вложенного юнита доступен только непосредственному родителю. Ребёнок не импортирует
родителя, предков или соседних детей; родитель связывает детей через их контракты.

### Фасеты и среды

| Маркер | Потребление и назначение | Среда |
| --- | --- | --- |
| `index.ts` | Статический импорт через путь юнита; типы, чистые значения и совместимые UI-проекции | RSC, серверный prerender и браузер |
| `client.ts` | Статический импорт через `<unit>/client`; директива `'use client'` и клиентский API | Клиентская framework-граница с серверным prerender |
| `server.ts` | Импорт через `<unit>/server`; `import 'server-only'` и серверный API | Сервер Next.js: RSC и Route Handlers |

Каждый маркер объявляет юнит. Фасет содержит только директиву среды при необходимости и явные
экспорты для фактических потребителей. Один исполняемый экспорт принадлежит одному фасету.
Группы и внутренние сегменты не имеют фасетов; пустые маркеры и локальные barrels с этими именами запрещены.

- `index.ts` не достигает специализированного клиентского фасета или несовместимого runtime-кода.
- `client.ts` совместим с prerender: browser API читаются только в клиентском lifecycle.
- RSC-композиции с клиентскими блоками публикуются через `server.ts`; серверная реализация
  недостижима из универсального или клиентского графа. RSC может подключать Client Components через их фасеты.
- Отдельный browser-only API требует предварительного расширения профиля.
- Доменный UI, использующий модели и операции своего домена, остаётся внутренним компонентом
  без собственного фасета и при необходимости публикуется через фасет домена.

### Структура юнитов и композиций

Имена файлов и папок — `kebab-case`. Экран — `<name>.screen.tsx`, каркас — `<name>.layout.tsx`.
Словарь и смысл сегментов — по [React Reference](../../.claude/skills/react-reference/reference/application/architecture/project-profile.md#структура-юнита):
`config`, `helpers`, `hooks`, `operations`, `providers`, `stores`, `styles`, `types`, `ui`;
в доменах также `adapters`, `mappers`, `errors`, `source-errors`.
Полностью генерируемый `generated` принадлежит генератору, его внутренние barrels не объявляют юниты.

Каждый компонент имеет свою папку, props — `types/<name>-props.type.ts`, собственные стили —
`styles/<name>.module.css`. CSS Module не пересекает границу владельца; у компонента без DOM
нет фиктивной обёртки. Для экранов обязателен полный каркас, описанный в протоколе выше.
Прикладные TSX создаются через `pnpm run create` из `apps/next-web-app` и локальные `.templates`.
Порядок генерации — в [.templates/README.md](.templates/README.md) и
[template-generation](../../.agents/skills/template-generation/SKILL.md).

Группы `compositions`:

- `layouts` — постоянная компоновка приложения или ветки, принимает содержимое через `children`;
- `screens` — законченные экранные проекции и состояния, подключаемые framework-страницей;
- `route-boundaries` — самостоятельное поведение ветки: доступ, параметры, область Provider или выбор экрана;
- `widgets` — крупные самостоятельные области с прямыми потребителями вне одного владельца.

Группы классифицируют юниты и не имеют реализации или API. Вёрстка колоцируется у ближайшего
владельца; самостоятельные области выделяются во вложенные юниты, технические обёртки остаются
внутренней разметкой. Пустые слои, сегменты и группы не создаются.

### Граница Next.js и технические владельцы

`src/app/layout.tsx` задаёт `html`/`body`, инициализацию документа и подключение готовых фасетов.
`page.tsx` подключает экран, адаптирует framework-пропсы и объявляет metadata. Служебные
`params`/`searchParams` не передаются в DOM. Разметка и реализации Providers находятся вне `app`.

Тема, настройки и общие стили принадлежат `ui/themes`: Provider — в `client.ts`, безопасная
инициализация цветовой схемы — в `index.ts`. Global CSS подключается один раз через Provider;
`media.css` используется PostCSS. В RSC применяются именованные экспорты Mantine, например
`AppShellHeader`, по [инструкции Mantine 8 + Next.js](https://v8.mantine.dev/guides/next/).

Транспорт принадлежит `infra/client-api`, generated SDK — `packages/client-rest-api-sdk`.
Браузерный и публичный серверный клиенты имеют отдельные runtime-настройки; SSR-клиент
не получает credentials. Предметные адаптеры, приватные SWR-ключи и действия принадлежат доменам.
Граница авторизации определяется разделом выше, настройка адресов — [README.md](README.md)
и [env.example](env.example). Правила SDK — в
[rest-api-codegen-ru](../../.agents/skills/rest-api-codegen-ru/SKILL.md).
Стартовая страница API не вызывает. Отсутствие её обращений к API не является основанием
для удаления `infra/client-api`, `infra/diagnostics` или их зависимостей.
Публичный серверный клиент сохраняет пустое дерево, пока API не предоставляет независимые от авторизации операции.

| Правило React Reference для SPA | Адаптация Next.js |
| --- | --- |
| Vite, `createRoot`, отдельная HTML-точка входа | Next.js управляет запуском и гидратацией через корневой layout. [Installation](https://nextjs.org/docs/app/getting-started/installation) |
| React Router, `Outlet` и маршрутный `lazy.ts` | App Router задаёт URL, layout получает `children`, ссылки используют `next/link`. [Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages) |
| Публикация Provider через обычный фасет | Клиентский Provider публикуется через `client.ts`, безопасная инициализация — через `index.ts`. [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) |
| Чтение GET через SWR | Независимые от авторизации данные могут загружаться async Server Components; приватное чтение остаётся браузерным. [Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data) |

Команды проверок из корня репозитория:

```sh
PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false pnpm run web:lint
PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false pnpm run web:check-types
PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false pnpm run web:build
```

Корневые команды используют Turborepo и предварительную сборку SDK через `dependsOn: ["^build"]`.
Используй `PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false` для `pnpm run/exec`, чтобы проверки
не запускали автоматическое обновление зависимостей. Установку и lockfile согласовывай отдельно.
Стандартный ESLint Next.js не валидирует Unit Architecture; архитектурный граф проверяется отдельно.
Изменения SSR и клиентских границ дополнительно проверяются на production HTML, RSC и гидратации.
