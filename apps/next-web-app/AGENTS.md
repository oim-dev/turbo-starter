# Разработка Next.js

Разрабатывай приложение строго по [unit-architecture](../../.agents/skills/unit-architecture/SKILL.md)
и локальному [архитектурному профилю](#архитектурный-профиль) Next.js.
**Инварианты Unit Architecture обязательны для серверного и клиентского кода без исключений.**

[React Reference](../../.agents/skills/react-reference/SKILL.md) обязателен как источник
практик разработки React: компонентов, типов, форм, состояния, стилей, генерации и качества кода.
Для нового и изменяемого кода действует строгий режим всех совместимых правил.

React Reference рассчитан на SPA. Применяй его инструкции в пределах совместимости
с Next.js App Router, RSC, SSR и гидратацией. Ограничения reference «только SPA»
описывают область его примеров и не запрещают серверные возможности этого приложения.
Framework-поведение проверяй по [документации Next.js](https://nextjs.org/docs)
для установленной версии. Используй механизмы Next.js вместо несовместимых SPA-механизмов.
Такая адаптация не отменяет архитектурные границы и остальные правила reference.
Само использование Next.js не является основанием игнорировать совместимые требования.

Контекст задачи, план и результаты проверок передавай в текущей рабочей сессии.
Команды запуска и настройки API описаны в [README.md](README.md).

Протокол обязателен для всех задач по `apps/next-web-app`, включая связанные изменения
вне приложения. Последующие разделы дополняют его, но не ослабляют его требования.

   перечитывай протокол заново и восстанавливай необходимые инструкции.
   Пересказ и память прошлых задач не заменяют источник.

   Разложи задачу на затронутые ответственности и прикладные области.
   Для каждой прочитай соответствующие главы Unit Architecture, разделы React Reference,
   правила кода и требуемые профильные skills. Для границ сред прочитай материалы
   Unit Architecture о Next.js и SSR и соответствующую документацию Next.js.
   Читай конкретные инструкции до выбора решения. Одного `SKILL.md` недостаточно.
   Не переноси SPA-профиль или дерево примера в Next.js автоматически.

3. **Обоснуй решение до реализации.**
   Исследуй код и потребителей. Определи ответственность, ближайшего владельца,
   слой, необходимость отдельного юнита, публичный контракт и зависимости.
   Проверь фасеты, вложенность, колокацию, отсутствие циклов и совместимость
   транзитивных импортов со средой. Выбирай владельца по ответственности.
   Для рендеринга и данных определи серверные и клиентские части, места загрузки,
   правила кеширования, передаваемый через границу контракт и поведение при прямом
   открытии URL и клиентской навигации. Учти границу авторизации ниже.
   Кратко зафиксируй: что и где меняется, по каким прочитанным инструкциям и как проверить.
   Для адаптации React Reference укажи конкретное правило, причину несовместимости
   и механизм Next.js со ссылкой на документацию; для уже описанной адаптации — на раздел ниже.
   Для изменений интерфейса до реализации зафиксируй UI/UX-решение по разделу
   «Проектирование интерфейса». Без него реализация UI запрещена.

4. **Соблюдай блокировку.**
   До фактического выполнения пунктов 1–3 запрещены правки, генерация кода
   и делегирование реализации. Разрешены исследование, уточнения и планирование.
   Если не определены владелец или применимые правила, необходимый источник недоступен
   либо остаётся неразрешённое противоречие — останови затронутую работу и уточни решение.
   Не заменяй отсутствующее правило предположением или собственным исключением.

5. **Реализуй строго по выбранным правилам.**
   Следуй прочитанным инструкциям во время всей разработки.
   Существующий код и привычные подходы не оправдывают нарушение правил.
   Соблюдай предписанные способы генерации и использования библиотек.
   Не отключай SSR и не превращай приложение в SPA ради соблюдения React Reference.
   Перед работой в новой области повтори пункты 2–3 для этой области.
   Не расширяй изменения на незатронутый код ради единообразия.

6. **Проверь соответствие до завершения.**
   Сверь результат с checklist Unit Architecture, локальным профилем Next.js

   Выполни проверки проекта, а затронутые веб-сценарии проверь через `agent-browser`
   в собственной изолированной сессии. Для изменений интерфейса обязательна
   визуальная и сценарная проверка по разделу «Проверка через agent-browser».
   Для изменений рендеринга, загрузки данных и границ сред проверь production build,
   серверный HTML, RSC и гидратацию затронутых маршрутов.
   Исправь нарушения. Успешные lint, typecheck и build не заменяют архитектурную

   проверке сообщи блокер, не объявляй приёмку завершённой.

## SSR и получение данных

Server Components — исходный выбор для экранов и серверной загрузки.
Клиентскую границу выделяй для конкретной интерактивности, состояния или browser API.
Наличие клиентского блока не требует перевода всего экрана или layout в Client Component.
Клиентский Provider может принимать серверное содержимое через `children`;
это не переносит переданное серверное поддерево в клиентский граф импортов.

| Сценарий | Правило |
| --- | --- |
| Публичные данные для первоначального содержимого страницы | Загружай в async Server Component через серверный доменный API и SDK; не откладывай первую загрузку до клиентского effect или SWR |
| Интерактивный блок без самостоятельной загрузки | Передавай подготовленные данные через props; SWR не требуется |
| Клиентская пагинация, фильтрация, повторная загрузка, polling | Используй доменные SWR-хуки в Client Components |
| Первоначальный SSR и последующее клиентское обновление публичных данных | Серверная загрузка плюс начальные данные для SWR с согласованными параметрами, ключом и политикой revalidation |
| Авторизационно-зависимые данные | Браузерная загрузка после проверки сессии; при SSR — нейтральная заглушка по контракту ниже |
| Императивный запрос или изменяющая операция | Вызывай доменную операцию; SWR не используется для mutations. Явно синхронизируй затронутые клиентские и серверные представления |

Пагинация через URL и серверную навигацию может оставаться серверной:
само наличие пагинации не требует SWR. SWR не заменяет SSR там, где требуется
первоначальное серверное содержимое, и не добавляется только ради передачи готовых props.

Маршрут предметных данных сохраняет владельцев в обеих средах:

```text
Server Component → domains/<владелец>/server → infra/client-api/server → SDK → API
Client Component → доменный SWR-хук → доменный адаптер → infra/client-api/client → SDK → API
```

Серверный вызов выполняется напрямую через готовые API владельцев, без SWR
и лишнего HTTP-запроса к собственному Route Handler. DTO, преобразования ответов,
транспорт и credentials не становятся ответственностью экранного компонента.
Примеры Next.js с запросом в `app/page.tsx` не отменяют границу `app` этого проекта.

- `'use client'` не отключает серверный prerender. Не читай `window`, `localStorage`
  и другие browser API при импорте или серверном рендере; используй браузерный lifecycle.
- Начальные серверный и клиентский рендеры должны совпадать. Не скрывай ошибки
  гидратации через ожидание mount, `ssr: false` или `suppressHydrationWarning`.
- Данные на границе Server → Client должны быть сериализуемы React и разрешены
  контрактом авторизации. Server-only код и секреты недостижимы из клиентского графа.
- Для серверных данных явно определи актуальность, режим рендеринга, кеширование
  и обновление с учётом версии Next.js и настроек `next.config.ts`.
  Наличие RSC само по себе не означает SSR на каждый запрос:
  статический prerender допустим, когда соответствует требованиям к данным.
- Проверяй фактическое поведение SDK и транспорта; не предполагай автоматическую
  поддержку кеширования и дедупликации Next.js. Кеш SWR и серверные кеши независимы;
  `mutate` не инвалидирует серверный кеш, а `router.refresh()` не заменяет его инвалидацию.

Основания: [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components),
[Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data),
[Caching and Revalidating без Cache Components](https://nextjs.org/docs/app/guides/caching-without-cache-components).

### Граница SSR и авторизации

Это контракт текущего приложения с браузерной Bearer-сессией, а не ограничение Next.js.
SSR данных применяется **только к данным, не зависящим от авторизации**.
Перед выбором среды проверь зависимость запроса, доступа и ответа от пользователя,
сессии, роли или прав. Публичность URL сама по себе не делает данные независимыми от авторизации.

- Авторизационно-зависимые данные загружай и отображай только в браузере после
  восстановления и проверки сессии. При SSR выводи нейтральную заглушку без персональных значений.
- На смешанной странице сохраняй SSR публичной части и заглушки приватных блоков.
- В этом приложении Next.js не читает credentials и не загружает приватные данные
  для SSR, metadata, RSC payload или начального клиентского кеша.
  Не передавай их с сервера через props или `fallbackData`.
- Начальные серверный и клиентский рендеры приватного блока показывают одинаковую
  заглушку. Загрузка запускается только в браузерном lifecycle после проверки сессии.
- Клиентский guard не защищает переданные Server Components: они могут выполниться
  до проверки guard. Не передавай под него серверное поддерево с приватной загрузкой или данными.
- Приватные SWR-ключи и кеш учитывают область сессии; при выходе или смене аккаунта
  прежние данные очищаются, а поздние ответы не принимаются в новую область.

## Проектирование интерфейса

Визуальная целостность, адаптивность и удобство обязательны наравне
с функциональностью. Интерфейс «лишь бы работало» не является готовым результатом.

1. **Сначала спроектируй.**
   До написания UI определи задачу пользователя, главное действие,
   иерархию информации, композицию блоков и поведение на разных ширинах.
   Выбери типографику, отступы, плотность, цвета и визуальные акценты.
   Кратко зафиксируй решение в плане; детализация соответствует масштабу задачи.
   Опирайся на макет и дизайн-систему проекта. Если макета нет,
   самостоятельно сформируй цельное визуальное решение.

2. **Создавай продуманный визуал.**
   Обеспечь читаемую иерархию, согласованные размеры и отступы,
   аккуратные выравнивания, достаточный контраст и ясный главный акцент.
   Используй тему, токены и компоненты проекта по React Reference.
   Готовые компоненты требуют осмысленной композиции и настройки:
   их наличие само по себе не обеспечивает качественный дизайн.

3. **Проектируй полный пользовательский сценарий.**
   Сделай понятными следующий шаг, результат действия и способ исправить ошибку.
   Предусмотри применимые состояния: загрузку, пустой результат, ошибку,
   успех и недоступность действия. Сохраняй ввод при исправимых ошибках,
   предотвращай повторную отправку и сразу показывай обратную связь.
   Используй понятные подписи и сообщения на языке пользователя.

4. **Обеспечь адаптивность и доступность.**
   Продумай перестроение навигации, блоков, таблиц и действий на узком экране.
   Учитывай длинный текст и разный объём данных. Исключи случайные переполнения,
   перекрытия и скачки компоновки.
   Обеспечь семантику, доступные названия, управление клавиатурой,
   видимый фокус и удобные области нажатия.
   Анимации должны помогать взаимодействию и учитывать reduced motion.

Серверное ожидание, streaming и клиентское обновление проектируй как части одного
интерфейса. Используй осмысленные `loading.tsx` и `Suspense`-состояния по сценарию.
Сохраняй визуальную устойчивость при загрузке и гидратации; повторное обновление
не должно без необходимости заменять уже показанное содержимое общей заглушкой.

## Архитектурный профиль

Область действия — `apps/next-web-app/src`, Next.js 16 App Router. Поддерживаются RSC,
серверный prerender Client Components и выполнение в браузере. Инварианты Unit Architecture
обязательны во всех средах. Этот профиль определяет соглашения Next.js вместо
SPA-специфичных соглашений [профиля React Reference](../../.agents/skills/react-reference/reference/application/architecture/project-profile.md);
совместимые правила reference сохраняются.

### Слои и зависимости

| Путь от `src` | Ответственность | Алиас |
| --- | --- | --- |
| `app` | Framework-файлы, дерево URL, metadata и подключение готовых API | `app/*` |
| `compositions` | Вёрстка, каркасы и экранные сценарии | `compositions/*` |
| `domains` | Предметные контракты, правила, операции и адаптация данных | `domains/*` |
| `infra` | Технические интеграции и ресурсы | `infra/*` |
| `ui` | Универсальные визуальные возможности и тема | `ui/*` |
| `shared` | Чистые детерминированные функции, типы и значения | `shared/*` |

Алиасы определяются в `tsconfig.json`; Next.js читает их напрямую. Межюнитные импорты
используют алиас слоя и публичный фасет, внутренние импорты владельца — относительные.

Разрешённые зависимости:

- `app` → все слои;
- `compositions` → `compositions`, `domains`, `infra`, `ui`, `shared`;
- `domains` → `domains`, `infra`, `ui`, `shared`;
- `infra` → `infra`, `ui`, `shared`;
- `ui` → `ui`, `shared`;
- `shared` → `shared`.

Граф ацикличен, включая динамические импорты, реэкспорты и `import type`.
Фасет вложенного юнита доступен только непосредственному родителю. Ребёнок не импортирует
родителя, предков или соседних детей; родитель связывает детей через их контракты.

### Фасеты и среды

| Маркер | Потребление и назначение | Среда |
| --- | --- | --- |
| `index.ts` | Статический импорт через путь юнита; типы, чистые значения и совместимые UI-проекции | RSC, серверный prerender и браузер |
| `client.ts` | Статический импорт через `<unit>/client`; директива `'use client'` и клиентский API | Клиентская framework-граница с серверным prerender |
| `server.ts` | Импорт через `<unit>/server`; `import 'server-only'` и серверный API | Сервер Next.js: RSC и Route Handlers |

Наличие маркера объявляет содержащую его папку юнитом; несколько фасетов принадлежат одному юниту.
Фасет содержит только директиву или защитный импорт среды при необходимости и явные
экспорты для фактических потребителей. Один исполняемый экспорт принадлежит одному фасету.
Группы и внутренние сегменты не имеют фасетов; пустые маркеры и локальные barrels с этими именами запрещены.

- `index.ts` не достигает специализированного клиентского фасета или несовместимого runtime-кода.
- `client.ts` совместим с prerender: browser API читаются только в клиентском lifecycle.
- RSC-композиции с клиентскими блоками публикуются через `server.ts`; серверная реализация
  недостижима из универсального или клиентского графа. RSC может подключать Client Components через их фасеты.
- Отдельный browser-only API требует предварительного расширения профиля.
- Доменный UI, использующий модели и операции своего домена, остаётся внутренним компонентом
  без собственного фасета и при необходимости публикуется через фасет домена.

### Структура юнитов и композиций

Имена файлов и папок — `kebab-case`. Экран — `<name>.screen.tsx`, каркас — `<name>.layout.tsx`.
Словарь и смысл сегментов — по [React Reference](../../.agents/skills/react-reference/reference/application/architecture/project-profile.md#структура-юнита):
`config`, `helpers`, `hooks`, `operations`, `providers`, `stores`, `styles`, `types`, `ui`;
в доменах также `adapters`, `mappers`, `errors`, `source-errors`.
Полностью генерируемый `generated` принадлежит генератору, его внутренние barrels не объявляют юниты.

Каждый компонент имеет свою папку, props — `types/<name>-props.type.ts`, собственные стили —
`styles/<name>.module.css`. CSS Module не пересекает границу владельца; у компонента без DOM
нет фиктивной обёртки. Экраны сохраняют полный каркас генератора: `props`, отдельный файл
типов, CSS Module и публичный фасет. Даже без собственных параметров оставляй
`ScreenParams`, `RootAttrs` и `ScreenProps`; не сокращай экран до функции без props.
Прикладные TSX создаются через `pnpm run create` из `apps/next-web-app` и локальные `.templates`.
Порядок генерации — в [.templates/README.md](.templates/README.md) и
[template-generation](../../.agents/skills/template-generation/SKILL.md).

Группы `compositions`:

- `layouts` — постоянная компоновка приложения или ветки, принимает содержимое через `children`;
- `screens` — законченные экранные проекции и состояния, подключаемые framework-страницей;
- `route-boundaries` — самостоятельное поведение ветки: доступ, параметры, область Provider или выбор экрана;
- `widgets` — крупные самостоятельные области с прямыми потребителями вне одного владельца.

Группы классифицируют юниты и не имеют реализации или API. Вёрстка колоцируется у ближайшего
владельца; самостоятельные области выделяются во вложенные юниты, технические обёртки остаются
внутренней разметкой. Пустые слои, сегменты и группы не создаются.

### Граница Next.js и технические владельцы

`src/app/layout.tsx` задаёт `html`/`body`, инициализацию документа и подключение готовых фасетов.
`page.tsx` подключает экран, адаптирует framework-пропсы и объявляет metadata. Служебные
`params`/`searchParams` не передаются в DOM. Разметка и реализации Providers находятся вне `app`.

Тема, настройки и общие стили принадлежат `ui/themes`: Provider — в `client.ts`, безопасная
инициализация цветовой схемы — в `index.ts`. Global CSS подключается один раз через Provider;
`media.css` используется PostCSS. В RSC применяются именованные экспорты Mantine, например
`AppShellHeader`, по [инструкции Mantine 8 + Next.js](https://v8.mantine.dev/guides/next/).

Транспорт принадлежит `infra/client-api`, generated SDK — `packages/client-rest-api-sdk`.
Браузерный и публичный серверный клиенты имеют отдельные runtime-настройки; SSR-клиент
не получает credentials. Предметные адаптеры, SWR-хуки, ключи и действия принадлежат доменам.
Граница авторизации определяется разделом выше, настройка адресов — [README.md](README.md)
и [.env.example](.env.example). Правила SDK — в
[rest-api-codegen-ru](../../.agents/skills/rest-api-codegen-ru/SKILL.md).
Стартовая страница API не вызывает. Отсутствие её обращений к API не является основанием
для удаления `infra/client-api`, `infra/diagnostics` или их зависимостей.
Публичный серверный клиент сохраняет пустое дерево, пока API не предоставляет независимые от авторизации операции.

| Правило React Reference для SPA | Адаптация Next.js |
| --- | --- |
| Vite, `createRoot`, отдельная HTML-точка входа | Next.js управляет запуском и гидратацией через корневой layout. [Installation](https://nextjs.org/docs/app/getting-started/installation) |
| React Router, `Outlet` и маршрутный `lazy.ts` | App Router задаёт URL, layout получает `children`, ссылки используют `next/link`. [Layouts and Pages](https://nextjs.org/docs/app/getting-started/layouts-and-pages) |
| Публикация Provider через обычный фасет | Клиентский Provider публикуется через `client.ts`, безопасная инициализация — через `index.ts`. [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) |
| Чтение GET для отображения через SWR | Первоначальные публичные данные загружаются в Server Components; SWR обслуживает клиентскую загрузку и обновление по разделу [SSR и получение данных](#ssr-и-получение-данных). [Fetching Data](https://nextjs.org/docs/app/getting-started/fetching-data) |

## Проверка через agent-browser

Инструмент закреплён в devDependencies этого приложения и используется любым
кодовым агентом через CLI. Все команды ниже выполняются из `apps/next-web-app`.
Запускай `pnpm run browser <команда>`, чтобы использовать установленную проектную версию
и явный конфиг [agent-browser.json](agent-browser.json).
Перед первым запуском на машине выполни `pnpm run browser:install`.
Установка и примеры описаны в [README](README.md#браузерный-инструмент).

1. **Подготовь проверку.**
   Прочитай актуальную инструкцию `pnpm run browser skills get core` и проверь
   доступные команды через `pnpm run browser --help`.
   Для каждой задачи всегда создавай собственную изолированную сессию
   `agent-browser` с уникальным именем. Явно указывай её во всех командах,
   включая закрытие. Использовать сессию по умолчанию, общие или чужие
   сессии запрещено. Не переключай и не закрывай чужие вкладки и сессии.
   Дополнительная вкладка в общей сессии не считается изоляцией.
   Используй headless-браузер проекта без пользовательского профиля, `--cdp`
   и `--auto-connect`; `--headed` допустим по явному запросу пользователя.
   Не полагайся на сохранение shell-переменных между вызовами инструментов:
   повторяй выбранное имя через `--session <имя>` в каждом вызове.
   Открой работающее приложение и воспроизведи затронутый сценарий.

2. **Проверь поведение.**
   Пройди сценарий от входа до результата: навигацию, ввод, отправку,
   применимые ошибки и восстановление после них.
   Проверь клавиатуру и фокус, ошибки браузерной консоли и запросов.
   Проверяй наблюдаемый результат действия, а не только успешность клика.
   После переходов и изменения страницы обновляй `snapshot -i`; ожидай
   конкретный текст, элемент или URL. Смену аккаунтов проверяй в одной сессии,
   синхронизацию авторизации — в нескольких вкладках этой же сессии.
   Конфиг отключает автоматическое принятие `alert` и `beforeunload`:
   проверяй диалоги через `dialog status` и явно выбирай `dialog accept`
   или `dialog dismiss` по проверяемому сценарию.

3. **Проверь внешний вид и доработай.**
   Сделай и просмотри скриншоты на узкой, промежуточной и широкой ширине.
   Сравни результат с макетом или зафиксированным UI/UX-решением:
   композицию, типографику, отступы, акценты и состояния.
   DOM-снимок не заменяет просмотр изображения.
   Исправляй обнаруженные недостатки и повторяй затронутые проверки
   до выполнения критериев качества.

4. **Проверь SSR и гидратацию.**
   Для изменений рендеринга, загрузки данных и границ сред используй production
   build/start по README. Проверь прямое открытие URL, перезагрузку, клиентские
   переходы и изменение параметров маршрута, если они затронуты.
   Проверь исходный HTTP HTML и RSC payload: ожидаемое публичное содержимое приходит
   с сервера, с учётом streaming, а не появляется впервые после клиентского запроса.
   DOM после гидратации сам по себе не доказывает SSR.
   Проверь отсутствие ошибок гидратации, работоспособность интерактивности и
   сохранение ожидаемого состояния при переходах и обновлениях.
   Для auth-сценариев проверь HTML и RSC с действующей сессией: приватные данные
   отсутствуют в серверных ответах и появляются в интерфейсе только через
   браузерную загрузку после проверки сессии.
   При изменении кеширования проверь актуальность результата после повторного
   открытия, смены параметров и mutations, применимых к сценарию.

5. **Подтверди результат.**
   Кратко укажи проверенные сценарии, размеры viewport, результаты и пути к артефактам.
   Сохраняй скриншоты, HTML, трассировки и отчёты в корневом
   `.artifacts/next-web-app/<имя-сессии>/` по общим [правилам](../../AGENTS.md#артефакты-работы).
   Закрой собственную браузерную сессию через
   `pnpm run browser --session <имя> close`.
   Если обязательная проверка недоступна, сообщи конкретный блокер;
   не объявляй интерфейс полностью проверенным.

## Команды проверок

Из корня репозитория:

```sh
pnpm run web:lint
pnpm run web:check-types
pnpm run web:build
```

Корневые команды используют Turborepo и предварительную сборку SDK через `dependsOn: ["^build"]`.
Установку зависимостей и lockfile согласовывай отдельно.
Стандартный ESLint Next.js не валидирует Unit Architecture; архитектурный граф проверяется отдельно.
