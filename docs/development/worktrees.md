# Worktree-окружения

Каждая независимо выполняемая задача получает ветку, рабочую копию монорепозитория,
четыре env-файла и собственную инфраструктуру. Приложения работают на host,
PostgreSQL, MinIO, RabbitMQ и imgproxy — в Docker.

Требования: Linux с `/proc` и `flock` (util-linux), Node.js 24+, pnpm версии из
`packageManager`, Git и локальный Docker Engine с Compose v2. Команды выполняются
из любой рабочей копии того же Git-репозитория. Права на Docker должны быть настроены.

## Создание

```bash
pnpm worktree:create task-123
```

Создаётся новая ветка `work/task-123` из `HEAD`. Рабочая копия размещается в
`~/worktrees/github.com/oim-dev/turbo-starter/task-123`, если origin — этот репозиторий.
SSH- и HTTPS-адреса нормализуются к одному пути: протокол, пользователь и `.git`
убираются; хост и полный путь владельца сохраняются. Нестандартный порт сохраняется
в идентификаторе хоста. SSH-алиас автоматически не раскрывается: используйте `--repo`.

Перед созданием зафиксируйте исходные изменения: worktree получает содержимое
коммита, а не незакоммиченные файлы основной папки. Уже существующая ветка или каталог
не перезаписываются. При повторной задаче выберите новое имя либо заранее переименуйте
сохранённую ветку обычными средствами Git.

Параметры:

```bash
pnpm worktree:create task-123 --base main --port-base 21000
pnpm worktree:create task-123 --repo https://github.com/company/product.git
pnpm worktree:create task-123 --root /путь/к/worktrees
```

`--repo` нужен после tiged, если origin ещё не задан. Указывайте адрес своего проекта.
`--root` и `--repo`, если использовались при создании, передавайте и остальным командам.
Перед работой AI-агента установите проектные скиллы командой `pnpm run setup`
из каталога созданного worktree.

Без `--port-base` выбирается свободный блок из десяти портов в диапазоне 20000–29999.
Проверяются занятые сокеты и записи остальных экземпляров под общей блокировкой.
Порядок: сайт, админка, Client API, Admin API, PostgreSQL, S3 API, MinIO Console,
AMQP, RabbitMQ Management, imgproxy. Назначение сохраняется до удаления окружения.
Если другой процесс позже занял порт, запуск завершается с ошибкой.

## Env-файлы

Создание копирует актуальные `.env.example` выбранного коммита:

| Каталог                  | Рабочий файл |
| ------------------------ | ------------ |
| `infra/dev`              | `.env`       |
| `apps/nest-backend`      | `.env`       |
| `apps/react-admin-panel` | `.env.local` |
| `apps/next-web-app`      | `.env.local` |

Подставляются имя Compose, порты и связанные URL, включая CORS MinIO и публичные
ссылки файлов/изображений. Dev-секреты и прочие значения остаются из примеров.
Структура проверяется `pnpm env:check`. При повторном запуске файлы не перезаписываются.
Порты, имя Compose, теги собственных образов и связанные адреса управляются окружением;
`up` проверяет их согласованность. Для другого набора портов создайте новое окружение.

Обычная локальная разработка продолжает использовать стандартные значения:
достаточно скопировать примеры и выполнить команды из корневого README.
Дополнительного корневого env-файла нет.

## Запуск и остановка

```bash
pnpm worktree:up task-123
```

Команда устанавливает зависимости с `--frozen-lockfile`, проверяет env, запускает
инфраструктуру с ожиданием healthchecks, применяет миграции к собственной БД,
затем запускает `pnpm dev` в терминале. SDK и Prisma Client собираются штатными
командами. Исходные файлы и зависимости других worktree не используются.
Кеш Turborepo явно размещается в локальном `.turbo/cache` каждого worktree,
поэтому удаляется вместе с ним.

Параметры приложений читаются из env-файлов этого экземпляра. Унаследованные
одноимённые настройки основной копии очищаются перед запуском. У Next.js порт
читается обёрткой до старта HTTP-сервера; перенос одного `PORT` в обычный env
без этой обёртки недостаточен.

```bash
pnpm worktree:status task-123
pnpm worktree:down task-123
```

`status` показывает пути, URL, процессы и контейнеры. `Ctrl+C` останавливает
приложения текущего `up`, инфраструктура сохраняется. `down` останавливает
приложения и контейнеры, сохраняя данные для повторного запуска.
Для управляемой остановки запускайте приложения через `worktree:up`:
процессы получают уникальный маркер экземпляра, сохраняемый при прохождении Turbo.

Владелец `admin/admin` создаётся автоматически на новой БД. Keycloak по умолчанию
выключен; для SSO отдельно настройте callback URL текущей админки в БД и у провайдера.
Исторические миграции ради портов worktree не изменяются.

## Удаление

```bash
pnpm worktree:remove task-123
```

Удаление последовательно:

1. Проверяет принадлежность рабочей копии и отсутствие незакоммиченных файлов.
2. Останавливает процессы, запущенные через `worktree:up` этого экземпляра.
3. Выполняет Compose down с удалением volumes и orphan-контейнеров.
4. Удаляет оставшиеся ресурсы с меткой его Compose-проекта и собственные образы MinIO,
   включая помеченные результаты предыдущих сборок.
5. Удаляет Git worktree вместе с env, `node_modules`, сборками, кешами и артефактами.
6. Удаляет запись окружения и освобождает назначенный набор портов.

**Данные PostgreSQL, MinIO и RabbitMQ этого экземпляра удаляются.** Ветка и её коммиты
сохраняются для интеграции. Незакоммиченные изменения блокируют удаление; для их
явного удаления предусмотрен `--force`. Общие Docker-образы, build cache и store pnpm
не очищаются; глобальный `docker system prune` не вызывается.

Если Docker недоступен, удаление останавливается: рабочая копия и запись остаются,
чтобы повторить команду после восстановления Docker. Текущий Docker context
сохраняется при создании; дальнейшие операции используют именно его.

Служебные записи и снимок Compose находятся в `~/worktrees/.state/`, отдельно от Git.
Они позволяют остановить инфраструктуру даже после изменения или удаления env/compose
внутри задачи. Записи сохраняются при неудачной подготовке; такое окружение можно
удалить той же командой. Маленькие lock-файлы в `.state` остаются для координации
конкурирующих команд; блокировки автоматически освобождаются после завершения процесса.
